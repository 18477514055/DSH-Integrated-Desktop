## 2026-09-26 内核 0.1.7 适配：图标跨世代（**这个插件一度整个不见了**）

用户原话：「那个多对话插件，它现在无法呈现出来了，或许不兼容，建议你进行一次优化。」

**根因（实测，不是推断）**：插件用的是 **0.1.5 那代的图标名** ——
`IconQueueOutline14` / `IconCheckOutline16` …（数字后缀 = 默认尺寸）。
内核 0.1.7 的 `dsh-client-ui-primitives` 里**没有这些名字**，只有
`IconXxxRegular` / `IconXxxMedium` / `IconXxxArtwork`（尺寸走 `size` 属性）。
⇒ 12 个图标全是 `undefined` ⇒ `h(undefined, …)` ⇒ **React error #130**
⇒ 官方对**每个槽位条目**有独立错误边界，条目被渲染成空。

**为什么以前查不出来**：现象是「`apply()` 跑了、两个槽位注册都 `ok:true`、界面上什么都没有」，
看起来像"没加载 / 不兼容"；`npm run plugin:check` 当时也只报"等 45 秒也没出现"。
真正的线索在**页面控制台**（那个脚本原来没抓）：

```
slot entry crashed in 'conversation.input.right': Error: Minified React error #130
```

⇒ 记一条定位手段：**槽位条目渲染期崩掉，只会出现在页面 console，不会出现在插件的任何自述里。**

**修法**：加 `iconAcrossGenerations(stem, size)` —— 按 0.1.7 的名字优先
（`Regular` → `Medium` → `Artwork` → 旧名字），**取不到就返回一个渲染 `null` 的组件**
（绝不能返回 `undefined`，那等于把整条条目再炸一次）。12 处调用点全部改走它。
⇒ 同一个包在 **0.1.5 与 0.1.7 上都能用**；将来某个图标再改名，也只是少一个图标，不会整个插件消失。

**复验（`npm run plugin:check`，真跑）**：修前 **8 项 FAIL**（触发按钮等 45 秒不出现、弹窗不渲染、
0 个输入框…）→ 修后 **3 项 FAIL**，界面与交互全过：触发按钮 / 弹窗 / 两行输入 /
模型下拉（搜索 354→16、来源胶囊、分组）/ `/` 命令 / `@` 引用 / 附件 / Esc 三级行为。

## 2026-09-26 内核 0.1.7 适配（二）：`create` 之后**必须先 retain** 才借得到 binding

**根因（官方契约变了，不是我们发送逻辑坏了）**：

```
sessions/service.d.ts:172-179
  Create a Host Session and publish its catalog row before resolving.
  Callers retain the returned identity before borrowing its binding.

sessions/service.d.ts:234-238
  binding(id)  Borrow an already-retained binding without extending its lifetime.
               @returns the live binding, or undefined WITHOUT a retained generation.
```

`create()` 只保证"会话进了目录"；**binding 只对"已 retain 的世代"存在**。
0.1.5 那代直接 `binding(id)` 就能拿到 ⇒ 旧写法在 0.1.7 上**必然返回空**，
于是每一行都在 ③ 那一步退化成「会话已创建，但拿不到它的会话面（binding 为空）」，
提示词与附件一条都发不出去 —— 而 `sessions/` 下**会话文件真的建出来了**，
所以现场的观感是"发送坏了"，实际是"借不到会话面"。

**修法（照官方的样子）** —— 官方调用点：`dsh-client-ui-workspace/lib/client.js:970`
与 `dsh-client-ui-sidebar-right/lib/client.js:5922`：

```js
const reference = S.retain(sessionId, { source: "multiSessionSend" });
await Promise.race([reference.ready.catch(() => null), sleep(10000)]);  // 有界等"初次打开"
const face = reference.binding.session;
… face.prompt(parts, "queue") …
reference.release();      // ★ 必须在发送完成之后：释放后 binding getter 会抛 "is released"
```

* `source` 只是引用计数标签（`SessionReferenceSourceMap`，**声明合并可扩展、运行时无校验**）：
  官方内置 `controllerOperation` / `gateway`，两个 UI 各自扩了 `mainView` / `sidebarView`；
  我们用 `multiSessionSend`，出问题时能在 `retainedBy` 里认出是谁借的。
* `reference.ready` 是"这个引用对**共享的初次 `Session.open()`** 的等待"——
  这里用 **10 秒上限的有界等待**：打开慢不该把整趟发送卡死（`prompt` 是"宿主受理"语义）。
* **保留 0.1.5 的退路**（`typeof S.retain !== "function"` 时仍走 `binding(id)`），
  所以同一个包在两个世代上都可用。

**复验（`npm run plugin:check`，真跑，连跑 4 次）**：修前 3 项 FAIL → 修后
**44 PASS / 0 FAIL**，且关键三条从"全盘没找到"变成真找到：

```
PASS  标记文本 A 出现在磁盘上的持久数据里  — storages\session_projcache\sessions\session-…json
PASS  标记文本 B 也出现在磁盘上            — storages\session_projcache\sessions\session-…json
PASS  附件的字节出现在宿主数据里            — attachments\v1\file-objects\79\79445cbb…
结果：全部 PASS
```

★ 一条通用教训：**内核升代时，先读一遍我们用到的那几个官方 `*.d.ts` 的注释**。
这次两处事故（图标名、`retain` 契约）都是**官方在注释里明写了**"要 retain 之后才能借 binding"，
只是 0.1.5 时代那么写也能跑，于是没人回头看。

## 曾踩过的坑

- **`ctx.slots.register` 必须包在 `ctx.slots.inject(槽位名, () => …)` 里，且是方法调用形式** ——
  槽位由父级 entry 声明，声明前 register 会**同步抛错**；摘成局部变量会丢 `this.ctx`。
- **不许用 `conversation.sendSession` 提交带附件的内容** —— 它会 await 乐观回显的"退休"，
  而新建会话没被跟随 ⇒ promise 可能**永不结算**、按钮永久卡在"发送中…"。
  改用 `fileUpload.upload` + `face.prompt()`（完成语义有界）。
- **命令菜单与 `@` 引用菜单的候选源**要判 `unavailable`，不能把"内核没提供"当成"没有候选"。
