# 内核 0.1.7 适配：两个真 bug、一个被我说错的结论（2026-09-26）

> 起因是用户把内核从 `0.1.5-rc.2` 升到 `0.1.7-rc.2` 之后提的两件事：
> ①「官方插件界面进了左侧栏，我把以前那个装/管插件的插件卸掉，**卸不掉**，是不是有冲突？」
> ②「检查一下我们现在的外壳和官方这个版本有什么冲突。」
>
> 本文件记三件事：**① 的答案（不是冲突）**、**② 查出来的两个真问题**、
> 以及**我一开始把其中一件事判错了**（写在最后一节，因为它比 bug 本身更值得记）。

---

## 一、「卸载失败」的答案：不是我们的冲突，是 pnpm 的供应链策略

用户在官方界面上卸载 `dsh-plugin-install`，**连试三次都失败**。
内核把每次插件操作的 pnpm 完整输出写在自己的日志里：

```
<profile>\.plugin-manager\logs\operation-<时间戳>\pnpm.log
```

三份（2026-09-26 00:50:14 / 00:50:25 / 00:50:56）内容**完全一样**：

```
Error: ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION
  × removing a package
  ╰─▶ 2 lockfile entries failed verification:
        dsh-connect-workbuddy@2.1.0 was published at 2026-09-25T03:31:32.687Z
        dsh-qoder-connect@0.1.9     was published at 2026-09-25T07:25:51.742Z
      within the minimumReleaseAge cutoff (2026-09-24T16:50:15.129Z)
```

三条要点：

1. **拦住卸载的是两个毫不相干的插件**（`dsh-connect-workbuddy` / `dsh-qoder-connect`）
   —— pnpm 校验的是**整份 lockfile**（105 条），只要有一条"太新"，**任何**插件操作都被挡。
2. `pnpm config get minimum-release-age` → `undefined`
   ⇒ 这是 **pnpm 12.3.4 自己的默认值（24 小时）**，不是谁配的。
   最早能重试的时刻：`2026-09-26T07:25:51Z` = **本地 15:25:51（UTC+8）**。
3. **那次卸载并不是"什么都没发生"** —— 它做了一半：

| 位置 | 状态 | 含义 |
|---|---|---|
| `dsh.profile.bundles` | **已经没有了** | 它**早就不再被加载**了 |
| `dependencies` + `node_modules` | **还在** | 官方面板照样列出它 ⇒ 点卸载还是失败 |

**出路两条**（推荐第一条）：

* **用我们外壳的「外壳设置 → 集成版插件」卸** —— 那条路**一次 pnpm 都不跑**
  （直接撤 profile 三处 + 删 `node_modules` 条目，**动手前先备份**），所以不会被这条策略挡。
  只读核对过：真实 B 家里 `listInstalled` 确实列得出它（`enabled: false`）。
* **等**过 24 小时（本地 15:25:51 之后）再点官方的卸载。

## 二、真 bug ①：内核 0.1.7 换布局 ⇒ **新用户一个插件都装不上**

### 现象与证据

外壳自己的日志（全新家 + 0.1.7，首启向导装插件）：

```
安装插件 dsh-int-archive-manager@0.2.0：ok=false changed=[…]
  profile 的 node_modules 不存在：…\dsh-home\profiles\web\node_modules
```

### 根因

| 内核 | profile 的 `node_modules` | 我们的落位逻辑 |
|---|---|---|
| `0.1.5` 那代 | 内核启动时装 `@deepseek-ai/dsh-base` ⇒ **总是存在** | 有地方可写 ⇒ 正常 |
| `0.1.7` 起 | 模块解析改由 `<DSH_HOME>\profiles\node_modules`（**拦截层**）承担 ⇒ **全新 profile 里根本没有它**，要等 pnpm 真跑过一次才出现 | `if (!isDir(nmDir)) 报错返回` ⇒ **装不上** |

★ **开发机上永远复现不出来**：那里的 `node_modules` 早就存在了。
所以这个 bug 必须由一个**只走全新家**的脚本盯着 —— 见下面 `npm run fresh:check`。

### 修法（**适配官方，不是绕过官方**）

`src/plugins.js` 新增并导出 `ensureProfileModules(nmDir)`：目录不在就**建一个空的**，
位置上是文件则**拒绝覆盖**。两个入口共用它：

* `src/plugin-install.js` 的 `connectIntoProfile`（首启向导 / 设置页走这条）
* `src/plugins.js` 的 `provision`（随包分发走这条；原来报 `pending: "node_modules-missing"`）
* `scripts/install-plugin.js`（开发机用，同样改成自建）

**为什么"建一个空目录"是对的**：我们走的本来就是 pnpm 的等价物
（`dsh-plugin-manager` 的 `addBundle` → `pnpm add`，pnpm 建的就是这个目录；
profile 的 `pnpm-workspace.yaml` 里 `nodeLinker: hoisted`）。Node 的解析顺序是
`<profile>\node_modules` → `<DSH_HOME>\profiles\node_modules` —— 空目录不影响第二层。
**实测**：真家里那个 `profiles\web\node_modules` 本来就是**实体目录**，
里面既有 pnpm 装的包、也有我们建的联接，两者一直共存。

⚠️ 只建**这一层**。绝不碰 `<DSH_HOME>\profiles\node_modules`（内核的世代拦截层，
内核启动时自己 heal；见 `$DSH_HOME/AGENTS.md` 第一条硬规矩）。

### 验收：`npm run fresh:check`（**新脚本**，15 条断言，真跑）

`scripts/fresh-install-check.js` —— 全程临时 `userData` + 临时 `DSH_HOME`，**不碰 B / A**：

| 段 | 做什么 |
|---|---|
| ① | **真起一次外壳 ＋ 真内核**，让它把全新 profile 建出来；顺手把「全新 profile 到底有没有 `node_modules`」这件事实**测出来并打印**（前提变了它会说） |
| ② | 在这个真·全新家上跑我们**真正的安装入口** `installFromDir` |
| ③ | 三处契约全查，并**穿过联接真读一次** `lib/client.js`（目录在 ≠ 读得到）；另加幂等与"装前必先备份" |
| ④ | **再起一次内核**，用 `boot-peek.js` 读 `__DSH_BOOT__.entries` 问**内核自己**：「你加载的客户端插件清单里有它吗」 |

实跑结果（2026-09-26）：

```
实测：全新 profile 的 node_modules 存在=false
PASS  ★（事实记录）全新 profile **没有** node_modules —— 这就是那条 bug 的前提
PASS  ★ installFromDir 在**全新家**上成功了（修之前这里必失败）
PASS  ★ node_modules 被**自己建出来**了（不是等内核）
PASS  ★ 穿过联接**真读得到** lib/client.js（目录在 ≠ 读得到）  — 63772 字节
PASS  内核的客户端插件清单（__DSH_BOOT__.entries）里真的有 dsh-int-multi-session
PASS  （正对照）entries 不是空的  — entries(65)
[fresh-install] 全部通过（15 条）
```

另在 `scripts/plugin-install-check.js` 加了第 ⑪ 段（9 条，不需要内核）：
两个入口都查、并留一条**回归护栏**「旧那句『profile 的 node_modules 不存在』没有再出现」。
`plugin-install-check` 现在 **114 OK / 0 FAIL**，`provision:check` 仍 **90 OK / 0 FAIL**。

### ★★ 写这条脚本时自己踩的坑（记下来，别再犯）

第一版 ④ 段报 `boot-peek 退出码=3`、`token 请求: 0`（连接被拒），
看起来像"内核没加载插件"。真因是**我的判据量错了对象**：

> `waitKernelReady()` 写的是"读 shell.log，里面有『内核就绪』就算就绪"。
> 而 `shell.log` 在**同一个临时目录里跨启动累加** ⇒ 第二次启动时它**立刻**返回 true，
> 内核其实还没起来。boot-peek 连上去被拒，它报的却是"页面里没有 `__DSH_BOOT__`"。

改成「只认**这一次启动之后新增**的那几行」（启动前记下日志长度）之后才全绿。
**"这一次"和"曾经有一次"是两件事** —— 判据必须锁前者。

## 三、我说错的那件事：侧栏文件树**不是**冲突（是测试没跟上官方新交互）

### 我当时的判断（错）

> 「0.1.7 的右侧栏改成了 `sidebar.panellist`，文件面板不是当前面板时行根本不在 DOM 里
> ⇒ 注入拿不到东西。」

### 实测出来的真相

`node scripts/ui-check.js files` 在 0.1.7 上 4 项 FAIL（`state=null root=null rows=0`）。
把右侧栏的结构打出来之后，原因很清楚（**不是注入坏了**）：

* 0.1.7 的右侧栏变成了**可停靠的标签坞**（dock，`dsh-client-ui-sidebar-right`）。
  `defaultSeed(tabs)`（`client.js:584-593`）的规则是：
  **注册的标签类型只有一个**时才默认打开它，**否则默认落在「指南」页** ——
  一个罗盘 ＋ 每个已注册类型一个入口胶囊，点胶囊才 `openTab(kind, {replaceTab:true})`（第 530 行）。
* 文件树只是其中一个**类型**（`dsh-client-ui-sidebar-files`，`kind = "files"`），
  它的正文只有在**那个标签真的打开着**时才渲染。
  0.1.7 至少注册了 `files` 与 `terminal` 两类 ⇒ 展开右侧栏默认看到的是**指南**。
* **官方那两行 DOM 一个字都没变**：`data-files-entry` / `data-files-path` 仍在
  `sidebar-files/lib/client.js:498/499/522/523/542/543`，
  `data-files-state="tree"` / `data-files-root` 仍在 `657-660`。
* 我们的注入脚本（`src/inject/sidebar-open.js`）**一行都不用改** ——
  它监听的是整个 `document` 的 `mouseover`，行一出现就生效。

⇒ **修的是验收脚本**：`ui-check.js` 的 ④ 段从"睡 1.5 秒读一次"改成
「轮询等待 ＋ 若停在指南页就**点开 `files` 那个入口** ＋ 失败时打印右侧栏结构快照」。

★ 还有一层坑：指南入口要**挑真的能点的那一个**。实测页面里存在**两份**标签坞
（`role="tab"` 里「开始」出现两次），先命中的那份是**隐藏的**，
按它的坐标真点等于点空气（第一版就是这么假 FAIL 的）。
判据用 `elementFromPoint(入口中心)` 命中的是不是它自己
—— 与项目里已经写过三次的「矩形会骗人」是同一条。

修完：`node scripts/ui-check.js files` → **「files 模式全部通过」**
（含"真鼠标悬停 ⇒ 行尾浮出图标"、"真点 ⇒ 主进程 shell.log 留下独立一行"、
以及工作区外/`..` 穿越被拒的边界）。

### 用户实际会看到什么（这条不是 bug，但要知道）

升级到 0.1.7 之后，展开右侧栏**默认看到的是「指南」页**（两个入口：工作区文件 / 新建终端），
要点一下「工作区文件」才看到文件树 —— **这是内核自己的交互改动**，不是我们丢了功能。
文件树一出来，我们的悬停图标与右键菜单照旧。

### ★★ 修这一段的路上又挖出一个**量具级**的坑（比上面那个值钱）

改完标签坞之后**连跑 4 次**（项目规矩：flaky 要跑到稳），结果 **第 4 跑挂了**。
挂的位置跟我刚改的地方**无关**：是 ⑥ 段"真点一下『在文件资源管理器中显示』图标"
—— `calls=0`（点击事件根本没到我们那个按钮上）。

这里的处理顺序值得记下来：**先加量具，再改代码**。

第一步，把「点之前」和「点之后」的事实都打出来（在 `document` 上装一个**只数数**的
捕获监听器，`files` 模式里那段 `__clickLog`）。实测拿到的原文：

```
点前 {"stripDisplay":"flex","hoverPath":"…\\ws/note.txt","calls":0,
      "rect":[1226,117,22,22],"under":"BUTTON[reveal]"}
实际收到的 click=[]          ← 页面上的捕获监听器**一条都没收到**
```

**位置对、元素对、我们的状态也对，事件压根没到页面。** 这一条把"点空了 / 状态被清了 /
坐标过期"三种猜测全部排除掉 —— 都不是。

第二步才动代码，真因是**CDP 的输入事件跨连接不保序**：

> `realClick()` 原本是三次独立的 `cdpSend`（= 开三条 WebSocket，各自发完就关）。
> Chromium 对**不同 CDP 连接**的输入事件**不保证先后** ⇒ 偶尔"按下与抬起被重排"
> ⇒ **根本不会合成 click 事件**。

改成**三条事件走在同一条连接上**（同一个会话里 id 递增），再连跑 4 次：
**4/4 全过，而且每次都是一次就成**（不再出现"要点 4 次"）。

⚠️ 这条坑不只在 `files` 模式 ——`pages` / `plugins` / `firstrun` 都用同一个
`realClick()`，所以这是一次**全脚本级的**加固（已回归 `pages`）。教训与 §二的 ① 同源：
**"偶尔失败"要先问"我的量具是不是在撒谎"，别急着改被测对象。**

* **`ui-check plugins`**：外壳侧全绿；唯一失败是**下载插件超时**
  （`net::ERR_CONNECTION_TIMED_OUT` —— 本机 Clash 7897 当前没在跑），**与本次改动无关**。

  **预期**（产物是 0.2.15 那次构建的）。重新打包后自然消掉；
  已给这两个文件加了标记（`ensureProfileModules` 等），防止这个修复在将来被悄悄丢掉。
* **`ui-check pages` / `firstrun`**：前者本地那段此前已全绿（外部站点那段当前只能 SKIP）；
  后者要联网拉插件清单，当前**测不了**（同一个代理原因）。
