# 侧边栏文件「真打开」（2026-09-23）

> 用户原话：「右边的这个侧边栏展开后不是可以查看工作区文件吗？……我希望他加一点点功能。
> 就是我真的可以在侧边栏点击文件夹，点击文件来打开它（也就是点击这个动作，有两个功能，
> 一个功能是打开，然后读它，另外一个功能就是，相当于在文件管理器中点击他的能力）」

**做了什么**：侧栏文件树那一行，鼠标移上去时行尾浮出小图标 ——
**用默认应用打开** / **在文件资源管理器中显示**；右键任意一行还有菜单（含**复制路径**）。
**单击照旧是在侧栏里读它**（内核自带的行为，一个字都没改）。

**改动落点**：外壳（`src/inject/sidebar-open.js` + `src/main.js` 的 IPC + `src/preload.js`），
**没有碰内核任何一个文件**。

---

## 1. 为什么是外壳，不是"做一个侧边栏插件"

| 事实 | 依据 |
|---|---|
| 右侧边栏是**内核自带的 Web 客户端插件**，不是我们的外壳 | `@deepseek-ai/dsh-client-ui-sidebar-right`（面板 + tab 系统）、`-sidebar-files`（文件树本体） |
| 它的每一行**已经带着绝对路径** | `dsh-client-ui-sidebar-files/lib/client.js` 的 `Entry`：`<li data-files-entry="file" data-files-path="…">`，路径由 `childPath(state.root, entry.name)` 拼出，`state.root` 取自会话 cwd |
| **网页拿不到 Electron 的 `shell`** | 渲染进程里没有 `require("electron")` |
| 内核虽然有一条现成的"打开路径"通道，但**外挂插件够不着** | `dsh-api-session-controller` 的 `openWorkspacePath`（底层 `dsh-native-command` 的 `openNativePath` / `revealNativePath`）是**宿主半边**的一等公民服务；`ui-deliverables` 能用是因为它有宿主半边注册的 `/api/present.open` 路由 |

⇒ 按项目 AGENTS.md §1 的判断顺序：**先问能不能进外壳**。
这不只是"能进"，而是"**只有外壳能**"（要 Electron 的 `shell`），所以进外壳是唯一正确的落点。
（顺带：这样也不违反"不改内核任何文件、内核可独立升级"这条架构前提。）

## 2. 三个动作，各自的边界

注入脚本是 `src/inject/sidebar-open.js`，通道是 `window.dshShell.openWorkspaceFile(path, action)`。

| action | 主进程做什么 | 用户看到 |
|---|---|---|
| `open` | `shell.openPath(real)` | 用系统默认应用打开（`.txt` → 记事本、`.md` → 你关联的编辑器……） |
| `reveal` | `shell.showItemInFolder(real)` | 资源管理器打开并**选中**它 |
| `copy` | 页面自己写剪贴板 | 只复制路径，不碰文件系统 |

三个动作**全是只读**：不写文件、不删文件、不改任何东西。
（`reveal` 刻意用它、而不是 `shell.openPath(父目录)`：要的是"**选中**它"，
与内核 `revealNativePath` 同一个口径。Explorer 收下请求后常常返回非 0 —— 那**不代表失败**，
请求已经交出去了，所以不拿返回值当判据。）

`copy` 在主进程里**没有对应分支** —— 它是纯页面内的动作（`navigator.clipboard`，
被拒时退回临时 `textarea` + `execCommand`）。路径根本不出渲染进程。

## 3. 安全边界（**这三条缺一条，这功能就变成"从任意网页启动任意程序"**）

```js
const FILE_OPEN_ACTIONS = new Set(["open", "reveal"]);   // ③ 取值写死
```

| # | 闸门 | 怎么判 | 为什么不能省 |
|---|---|---|---|
| ① | **来源** | `assertLocalFileUi`：必须是**主窗口**，且 `event.senderFrame.url` 的 origin **就是本机内核**（`serverUrl`） | 两个外部站点视图（chat / platform）**共用同一份 preload** ⇒ `openWorkspaceFile` 在它们那儿**也存在**。光靠"有 preload"判来源 = 第三方页面白拿这个通道。（也不能用 `assertShellSender`：那只放行 `file://` 的外壳自有页面，而侧栏在 `http://127.0.0.1:<端口>`。） |
| ② | **路径** | `guardWorkspaceFilePath`：`realpathSync` 之后必须落在**已注册工作区**内（读 `$DSH_HOME/storages/workspace.json`，并上设置里那个工作目录兜底） | 否则通道就成了"打开任意路径"。**用 realpath 是刻意的**：本机 `plugin/` 下有 Junction 指到别的工作区，解析完再判才不会漏判或误判。**fail closed**（读不到注册表就只认设置里那一个）。 |
| ③ | **动作** | 只认 `open` / `reveal`，别的**归一成 open**，不会变成第三件事 | 未知动作直接透传的话，将来主进程多一个分支就等于凭空多一个能力 |

被拒时**一定写日志**（`侧栏打开被拒：…`），页面上还会弹一行红字提示 —— 不写的话
用户只会觉得"点了没反应"。

## 4. 注入脚本的四条硬约束（每条都是踩过的）

| # | 约束 | 为什么 |
|---|---|---|
| ① | 样式一律走 **CSSOM**（`el.style.foo = …`） | 官方页面可能下发严格 `style-src` ⇒ `<style>` 与 `style="…"` 会被拒 |
| ② | **不碰 `innerHTML`** | 有些页面开了 Trusted Types，赋 `innerHTML` 直接抛错。全部 `createElement` + `textContent` |
| ③ | 事件拦截挂**根节点 + 冒泡**阶段 | 在自身元素上用**捕获**阶段 `stopPropagation` 会让**同一元素冒泡阶段的监听器全部不执行**（Chromium 把目标节点的捕获监听器放在捕获趟里跑，一 stop 掉后面的目标趟被整个跳过）。症状极具误导性：元素在、监听器也在、`el.click()` 什么都不发生 |
| ④ | 控件**不塞进 React 的 DOM**，挂在 `document.documentElement` 的独立浮层上，用 `getBoundingClientRect()` 跟着行跑 | 树是 React 画的，append 进去的图标会在它重渲染那一行时被抹掉；独立浮层还顺带绕开了侧栏那几层 `overflow`（`absolute` 的子节点会被裁掉） |

**"看得见"的判据用 `elementFromPoint`，不用 `getBoundingClientRect`**：
矩形是**未裁切**的几何 —— 行被滚出可视区、或被别的层盖住时矩形照样正常。
每次出图标前都问一句"这一点上最上面的是谁"，命中的不是那一行就**不出**控件。
（假 PASS 比 FAIL 更糟，见项目 AGENTS.md §5。）

## 5. 验证：`node scripts/ui-check.js files`（21 项断言，真跑）

自己造一个**自足**的工作区夹具（1 个子目录 + 3 个文件 + 1 个真会话），
起临时内核真跑，然后：

- **真鼠标事件**（`Input.dispatchMouseEvent`）移到文件行上 —— `el.click()` 不产生
  `mouseover`，验不出"鼠标移上去才出现"这种东西；
- **真点**那个图标，然后回读**注入脚本自己的状态**（`calls` / `last`）
  ＋ **主进程的 `shell.log`** —— 两处都对上才算通（互不相关的第二份证据）；
- **越界必须被拒**：从页面里直接调通道，拿工作区外的真实文件 / `..` 穿越 / 空路径
  各打一遍，并要求主进程日志里留下「拒绝」；
- 位置判据用 `elementFromPoint`。

**2026-09-23 复验：连跑 4 次全过（21/21 × 4）。**
`pages` / `plugins` / `firstrun` 三个既有模式同时复跑，无回归。

## 6. ★★ 这一轮踩到的五个"量具/卫生"问题（比功能本身更值得记）

### 6.1 `el.click()` 关不掉官方那个首屏弹窗

全新家里官方会弹「内测声明」/「添加一个 API Key」两个对话框，都是
`position:fixed; z-index:1000` 的遮罩**盖满整屏**。它挡着的话后半段每条判据都会
莫名 FAIL。两个都要处理：

- **内测声明**：确认状态**持久化在 `DSH_HOME/settings.yaml`** 的
  `ui-onboarding.welcomeNoticeVersion`（真家里的值 = `2026-08-13.1`）⇒ 种一个"已确认"进去。
- **添加 API Key**：`el.click()` 能触发 React 处理函数，但那个框**不会真的关掉**
  （遮罩仍在）。必须用**真点击**。而且它**会弹回来** —— 判"关掉了"不能只看一次。

真因（读 `ui-settings-models` 源码）：`onboardingReadiness()` 只在
**一个可用 provider 都没有**时才走到 `credential-missing` 弹这个框。空夹具里当然没有
⇒ 那是**测试环境的假象**。种一份**假凭据**（`ui-check-dummy-not-a-real-key`）
让它变成 `provider-ready`，框就不再出现。
**不读、不打印、不复制任何真实密钥。**

### 6.2 判"工具就位"时，`getBoundingClientRect()` 也会骗人

`ui-check files` 第一版**4 跑 2 过**。抓到的现场是 `left=1273` 而视口只有 1264 宽
⇒ **那一行还在屏幕右侧外面**（右侧边栏还没滑进来），我却当它"稳定了"就往上移鼠标。
⇒ "就位"要同时满足两件事：矩形**连续两次不变**（动画停了）**且**它的中心真的落在视口里。

### 6.3 点"展开侧边栏"点成了"收起"

原来是"无脑点一下 toggle"。但面板的展开状态是**按会话**存的
（`state.bySession[sessionId].layout.expanded`），而 toggle 是**开关**不是"打开"
⇒ 它本来就开着时，我这一点反而把它**关上了**，整片判据全 FAIL。
⇒ 必须**先读状态、只在不展开时才点**，点完回读确认，并允许重试。
（核心里 `ExpandButton` 只在收起时渲染，所以优先按它。）

### 6.4 比路径时没归一分隔符 ⇒ 同一条日志"对不上"

页面给的 `data-files-path` 是斜杠混排（`…\ws/note.txt` —— 内核用 `/` 拼的），
而 `shell.log` 里是 Windows 原生反斜杠（`…\ws\note.txt`）。
直接 `includes()` 就是这么假 FAIL 的：**同一条日志，看着一模一样却对不上**。

### 6.5 ★★ 真跑的验收**会在用户桌面上留垃圾** —— 必须自己收拾

这个功能是真的调 `shell.showItemInFolder()`，所以**每跑一次 `files` 模式，
桌面上就多一个资源管理器窗口**（停在 `%TEMP%\dsh-uicheck-*\ws`）。
第一轮 4 跑 + 前面调试下来，用户桌面上堆了 **21 个**。

⇒ 脚本 `finally` 里加了 `closeStrayExplorerWindows(tmpDir)`：
用 PowerShell 的 `Shell.Application` COM 枚举窗口，**只关位置落在本次临时目录里**的那些
（用户自己的窗口一个都不动），失败只打日志、不影响判据。
**2026-09-23 复验：连跑 4 次之后桌面窗口数仍是 1（那 1 个是用户自己的）。**

> 教训：**"真跑"和"别弄脏用户的机器"要同时做到。**
> 验收脚本凡是会**弹出真实窗口 / 启动真实程序 / 写真实文件**的，
> 都要在收尾里把痕迹清掉 —— 否则用户会觉得"这个 AI 一跑东西我桌面上就一堆窗口"。

> **共同教训**：这五条没有一条是功能本身的 bug，全是**判据/量具/卫生的错**。
> 遇到 FAIL 先问"是我的尺子错了吗" —— 项目 AGENTS.md §5 早就写了这一条。
