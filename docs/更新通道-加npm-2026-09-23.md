# 更新通道：加上 npm（2026-09-23 用户提出）

> 用户原话：「虽然网盘途径的话每个人不一样，所以不一定能下载，但是呢我认为我们未来的这个
> 检查插件更新以及检查外壳更新完全可以加上这个 npm 通道，这样子的话也方便别人在没有梯子的
> 情况下检查和进行更新。」

**结论：赞成，而且这是这三条通道里唯一"对国内用户真的可达"的那条。** 本机实测证据在下面。

---

## 1. 为什么是 npm（本机实测，不是印象）

| 通道 | 本机实测结果 |
|---|---|
| **npm registry** | ✅ **不需要代理**：`npm ping` → PONG 475ms；`npm view` / `npm pack` 全程直连成功（2026-09-23 多次） |
| GitHub（现在是外壳更新的来源） | ❌ 需要代理，且当时**代理端口 7897 是关的**、`raw.githubusercontent.com` 直接重置 |

⇒ 对一个"没有梯子"的用户，**GitHub 上的检查更新等于不可用**，而 npm registry 可用。
而且**内核更新早就是走 npm 的**（`src/kernel-update.js` 查官方 `@deepseek-ai/dsh`，
下载 `.tgz` 并按官方 `dist.integrity` 校验）—— 这条路已经验证过，把同一套做法扩展到
插件与外壳是顺理成章的，不是新发明。

## 2. 三件事分别怎么做

| 要更新什么 | 现状 | 加 npm 通道怎么做 |
|---|---|---|
| **内核** | ✅ 已经是 npm 通道 | **不用动** |
| **插件** | 读一个 GitHub 上的索引清单（`src/plugin-catalog.js`） | ① 每个包查 `https://registry.npmjs.org/<包名>` → `dist-tags.latest` 比版本；② 下载走 `versions[<v>].dist.tarball`，校验 `dist.integrity`（sha512，registry 免费给）；③ **顺便可以让"插件清单"本身来自 npm**：`GET /-/v1/search?text=scope:<作用域>` 列出整个作用域下的包 ⇒ 索引不用手工维护 |
| **外壳** | 查 GitHub `releases/latest`，下载 `.exe` | 见下（这是唯一有取舍的一件） |

### 外壳那件：两个选项

| 选项 | 做法 | 代价 |
|---|---|---|
| **A（推荐先评估）** | 把安装包**作为一个 npm 包**发布（`@<scope>/dsh-integrated-desktop`），更新器从 registry 下 tarball、解出 `.exe`、按 `dist.integrity` 校验后启动安装器 | 每个版本要在 npm 上放 ~88 MB；npm 每个版本的包**不可覆盖**（必须升版本号）⇒ 每次发布都要升版本（我们本来就升） |
| **B（退一步）** | npm 上只放一个**很小的元数据包**（版本号 = 外壳版本，或带一个指向真实下载地址的字段）⇒ 只解决"**能不能检查到**" | 没有梯子的用户**仍然下载不到 exe** —— 只解决了一半 |

⇒ **建议：先做 B 的成本几乎为零（可以立刻有"检查"能力），同时评估 A 的体积/流程代价**；
真要"没梯子也能装"，A（或在国内放一个镜像/网盘直链，并把 npm 当索引）才是完整解。

## 3. 必须说清的三个代价

1. **公开**：npm 上的一切都是公开的（这条 2026-09-23 刚踩过：插件 README 被当成包页面的文章）。
   ⇒ 走 npm 的东西**必须按"给陌生人看"的标准写**；不想公开的就别发 npm。
2. **不可覆盖**：同一个版本号发过就不能再发 ⇒ 每次都要升版本号（`publish-release.py` 那条
   "按 tag 幂等、忘了改版本号会把上一版附件无声换掉"的坑，在 npm 上表现为**直接失败**，反而更安全）。
3. **发布要 2FA**：AI 起的子进程没有 TTY ⇒ **发布永远要用户自己在终端按**；
   但"检查更新/下载"不需要登录、不需要 TTY，AI 可以全程验证。

## 4. 落地清单（动手前先读一遍现有实现）

- [ ] `src/plugin-catalog.js`：加 npm 源（版本比较 + tarball + integrity），与现有 GitHub 索引**合并**，同名取新，并记录来源（现有代码已有 `sourceLabel` 之类的展示位）。
- [ ] `src/update.js`：加 npm 源（比 `dist-tags.latest` 与 `app.getVersion()`，沿用现有 `cmpVersion`）。
- [ ] `src/kernel-update.js`：**不动**（已达标，可作范本）。
- [ ] 界面文案说清"这一版是从哪条通道查到的"，别让用户以为只有一条路。
- [ ] **两条通道都试，取较新**；其中一条不通不能让整个检查失败（现在是单源，挂了就全挂）。

## 5. 验收怎么做（关键：要证明"没有梯子也能用"）

1. **真连一次 npm registry**，断言拿到 `latest` 与 `dist.integrity`（照 `kernel:check` 的写法）。
2. ★ **把代理关掉再跑一次**（Electron 用 `--no-proxy-server` 起）⇒ 断言：
   **npm 那条仍然成功、GitHub 那条失败**。这一条才真正证明用户的那句话成立。
3. 版本比较这把尺子单独验（`0.2.10 > 0.2.9`、预发布排在同版本正式版之前 —— 现有 `cmpVersion` 已覆盖）。
4. 下载后**按 `dist.integrity` 逐字节校验**，坏了就删（现有内核更新那套直接复用）。
