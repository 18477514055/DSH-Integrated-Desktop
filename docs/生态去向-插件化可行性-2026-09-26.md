# 生态去向：哪些功能能改成插件、官方桌面端能不能改（2026-09-26）

> 用户提的问题（这是**路线决策**，不是 bug）：
> 「很多功能已经通过插件实现了，但还有一些是直接注入外壳的，**它们能改成插件吗**？
>  以及**官方即将发布的桌面端能不能对他们的外壳进行改造**？
>  这决定我们究竟是继续坚持我们的生态，还是把生态迁移到官方桌面端上。」

结论先行：**继续坚持我们的生态，但把重心从"外壳注入"移到"内核插件"** ——
因为**插件跟着内核走（换外壳还能活），注入跟着外壳走（换外壳就死）**。

---

## 一、先把家底数清楚（实测，不是估计）

| 层 | 体量 | 内容 |
|---|---|---|
| **插件**（`plugin/`，9 个） | **725.9 KB**（`lib/*.js`） | 多会话、归档管理器、手机遥控、上下文上限、上下文查看器、模型路由、IM 文件收件箱、壁纸、缓存保持 |
| **外壳主进程**（`src/`，19 个文件） | 540.9 KB | 窗口/托盘/内核生命周期/更新/内核安装/首启向导/设置页/插件清单与安装/诊断 |
| ├ 其中**注入官方页面** | **3 个文件 / 55.7 KB** | `model-search.js`、`sidebar-open.js`、`page-switch.js` |

⇒ 生态**已经**是"插件为主"：插件体量（726 KB）**超过外壳主体**（541 KB），
而"注入"只占外壳的 **10%**。所以"迁移"要动的是这一小块，不是全部重写。

## 二、能力分层：一件事能做在哪一层（这是判断"能不能改成插件"的唯一尺子）

| 层 | 谁在跑 | 拿得到什么 | 拿不到什么 |
|---|---|---|---|
| **① Electron 外壳**（`src/main.js`） | 我们自己打包的 app | 窗口/托盘/单实例/全局键、`WebContentsView`、`app.getPath`、`net`（走系统代理）、自更新、`spawn` 内核、**在任何内核存在之前就能跑** | 官方页面里的 DOM（要注入）、内核的一等公民服务（要绕 IPC） |
| **② 插件·宿主半边**（`dsh.bundle.patch` + cordis） | **内核进程里** | fs / net / child_process、官方宿主服务（`sessionController`、`dsh-native-command` 的 openNativePath / revealNativePath、fileUpload、commands…）、**自注册 HTTP 路由** | Electron 的任何东西（内核是纯 Node；它连窗口都没有） |
| **③ 插件·客户端半边**（`dsh.client`） | 官方 Web 页面里 | **官方页面的完整 DOM**、React 槽位（`ctx.slots`）、`ctx.remote.*` RPC（可调自己宿主半边的路由）、localStorage、WebSocket | ① 与 ② 之外的：没有 Electron、不能自己开窗口/托盘 |

★ 关键推论：**"注入外壳"能做的事，绝大多数在 ③+② 里都能做** ——
因为 ③ 就在同一个页面里（DOM 一样能改），② 在内核进程里（文件、网络、系统动作一样能做）。
唯一的不可替代是 **①**。

## 三、逐个功能的判定（我们现有的东西，一条一条判）

### A. 已经是插件（9 个）—— **跟着内核走**

多会话 / 归档管理器 / 手机遥控 / 上下文上限 / 上下文查看器 / 模型路由 /
IM 文件收件箱 / 壁纸 / 缓存保持。

⇒ **换任何外壳（包括官方桌面端）都还在**，只要它们被装进那个外壳所用的 **profile**。

### B. 外壳注入（3 个）—— **技术上都能插件化，但难度分三档**

| 注入 | 它做什么 | 改成插件？ | 依据 / 成本 |
|---|---|---|---|
| `model-search.js` | 官方「选择模型」菜单加搜索框 + 提供方胶囊 | ✅ **能，成本低** | **我们已经有等价实现**：`dsh-multi-session` 里那份 `.dshms-*` 搜索 + 来源胶囊就是它的孪生（`plugin-check` 真跑通过：搜 354→16、胶囊筛选、Esc 三级）。抽出来就是插件 |
| `sidebar-open.js` | 侧栏文件的「用默认应用打开 / 在资源管理器显示」 | ✅ **能，中等成本** | 需要系统动作 ⇒ 搬到插件**宿主半边**：官方有 `dsh-native-command` 的 `openNativePath`/`revealNativePath`，或像手机遥控那样自注册宿主路由。路径越界守卫（现在在 `main.js` 的 `guardWorkspaceFilePath`）可原样搬 |
| `page-switch.js` | 右侧边缘把手 + 三页切换面板 | ⚠️ **UI 能搬，能力搬不了** | 把手/面板本身是 DOM ⇒ 能做成插件 UI；但真正"把 chat.deepseek.com 装进同一个窗口"要 `WebContentsView` ⇒ **只有 ① 能做**。官网带 `X-Frame-Options`，iframe 这条路是死的（2026-09-22 实测过） |

### C. 外壳独有 —— **插件做不了，而且这正是外壳存在的理由**

| 功能 | 为什么只能是外壳 |
|---|---|
| **引导层**：内核发现/安装（随包带 npm ⇒ 用户不必装 Node）/启动/健康检查/重试 | 插件**必须**先有内核才能加载（鸡生蛋） |
| **首启向导** | 全新家里一个插件都没有，UI 得先存在 |
| **外壳自更新、内核更新检查** | 要动的是"正在运行的 app/内核"本身 |
| 托盘 / 单实例 / 窗口状态 / 全局快捷键 | Electron 主进程 |
| 三页切换（`sites.js`） | `WebContentsView`（见上） |
| 加载页 / 状态页 / 诊断 / 外壳设置页 | 内核起不来时也得有界面 |

### D. 插件清单与安装（外壳里，但"可搬"）

`plugin-catalog.js` / `plugin-install.js` / `plugin-pack.js`（多来源 + sha256 校验 + 离线包）——
官方生态里对应的是 `dsh-plugin-manager` / `dsh-plugin-install`（用 pnpm 装）。
技术上能做成插件（宿主半边能读写 profile），**但"首启那一次"必须靠外壳**，
所以现状（外壳兜底 + 官方通道并存）是合理的，不建议搬。

## 四、官方桌面端：内核里已经有**硬证据**（不是猜的）

在内核 `0.1.7-rc.2`（本机全局 npm 那一份）里直接读到的：

| 证据 | 出处 | 说明 |
|---|---|---|
| `rejectElectronProfile()`：`profile "desktop" is managed exclusively by the Electron application` | `@deepseek-ai/dsh/lib/bin.js` | **内核为"官方 Electron 桌面端"预留了 `desktop` 档案**，CLI 一律不许碰它 |
| `PROFILE_TEMPLATES = { acp, web, headless, sdk, sdk-minimal }` —— **没有 `desktop`** | `dsh-app-boot/lib/types/profile.d.ts` 与实现 | ⇒ `desktop` 档案是**那个 app 自己带来并管理的**（"application-owned profile"） |
| `loadProfileDirectory(..., { userLayer?: boolean })`：`userLayer:false` 会**跳过用户的 `cordis.patch.yml`** | 同上 | ★★ **这正是一个"app 可以关掉第三方扩展"的官方机制** —— 会不会关是产品决策，只能等发布后实测 |
| `dsh-client-ui-sidebar-browser` + `electron/ElectronWebViewImpl` | 该包的 `lib/types/client/electron/` | 官方 UI **自己就有"侧栏内嵌浏览器"**，在官方桌面上走**真 Electron WebView**（原生侧实现、Web 侧出 UI） |
| preload 契约：主题镜像、`Optional Electron status presentation; the native shell owns actions and Web owns visible copy` | `dsh-client-ui-*` 的 `client.js` | 官方设计里**原生外壳 ↔ Web UI 之间本来就有桥**，但那座桥目前是**他们内部**的 |
| `.asar` → `.asar.unpacked` 路径处理、`ELECTRON_RUN_AS_NODE=1` 启动子进程 | `dsh-*` 多处 | 内核**被设计成可以跑在 Electron app 的 asar 里** |

⇒ 一句话：**官方桌面端就是"我们这条路"，只是他们自己走了** ——
Electron 外壳 + 内核 + 官方 Web UI，而且他们已经预留了 `desktop` 档案与原生↔Web 的桥。

## 五、两个问题的直接回答

### 问题一：注入外壳的那些，能改成插件吗？

**能 —— 3 个里有 2 个建议现在就改，第 3 个只能改一半。**

* 判据不是"能不能"，而是**它需要哪一层**（见 §二）：只要不需要 Electron 的窗口/托盘/视图层，
  ③（页面 DOM）+ ②（内核进程里的 fs/net/系统动作）就能覆盖。
* 我们已经有**两个成功先例**：`dsh-multi-session` 把"官方菜单里的搜索框 + 提供方胶囊"
  在插件里又实现了一遍（孪生）；`dsh-mobile-remote` 用**自注册的宿主路由**做了
  "跨设备看会话/发消息"这种相当"外壳级"的事。

### 问题二：官方桌面端能不能改造它的外壳？

要分两问，答案完全不同：

1. **"我们能不能去改他们的外壳？"** —— 技术上能（patch 他们的 asar / 注入他们的进程），
   **但不该做**：
   * 我们**已经吃过这个亏**：2026-09-17 改社区端安装目录里的官方包，升级/重装当场被冲掉；
   * 官方包是打包+签名的，改了等于把自己绑在一个**私有分支**上，每次更新都可能炸；
   * 多半违反他们的条款，而且我们**没有**任何回退通道（那是别人的 app）。
2. **"他们的外壳会不会给我们留官方扩展点？"** ——
   * **内核级：已经有了，而且我们正在用**：profile + bundle patch 层 + `--patch` +
     客户端槽位 + 宿主路由 —— 这套在官方桌面端上**同样存在**（同一个内核）。
   * **外壳级（native shell）：目前只有内部契约的证据**（preload 镜像主题/状态、
     `ElectronWebView` 由原生侧实现、`native shell owns actions and Web owns visible copy`），
     **没有任何"第三方可注册原生能力"的公开接口**。而且 §四 那条
     `userLayer:false` 说明他们**有能力**把第三方扩展关掉。
   * ⇒ **不要把生态押在"改造官方外壳"上**。要押就押在**插件**上。

## 六、建议（我的取舍）

**继续坚持我们的生态，但把重心从"外壳注入"移到"内核插件"。** 三步：

1. **把 2 个注入插件化**（`model-search` → 独立插件，孪生实现可直接抽；
   `sidebar-open` → 插件（宿主半边做系统动作））。这样它们在**任何外壳**上都能用。
   `page-switch` 的**把手**也可以插件化，但能力仍留外壳 —— 而且**先别加码**：
   官方已有 `sidebar-browser`/`ElectronWebView`，等看清他们的形态再决定要不要继续自己维护。
2. **插件安装器加"目标 profile"参数**（现在写死 `web`）：官方桌面端用的是 `desktop` 档案，
   档案之间**互相独立**（各自的 `package.json` / bundles / `node_modules`）。
   加上这个参数，官方桌面端发布当天我们就能做一次"把整套插件装进 `desktop` 档案"的实测 ——
   能用就双活，不能用也早知道。
3. **官方桌面端发布后必测三件事**（决定要不要真的迁移）：
   ① 它的 `desktop` 档案**收不收第三方 bundle**（看它有没有用 `userLayer:false` / 限定 bundles）；
   ② 它的客户端**槽位**是否照旧（我们的插件靠 `ctx.slots` 渲染）；
   ③ 它的原生桥（`ElectronWebView` 等）**开不开放给插件** —— 那决定我们的"三页切换"要不要退休。

★ 一句话原则：**凡是"只有外壳能做"的，留在外壳；凡是"内核能给"的，一律做成插件。**
前者是我们的护城河（引导层 + 原生体验），后者才是**能跨外壳复用的生态资产**。
