# 「无法彻底退出 dsh，从托盘退出也不行」——根因与修复（2026-09-23）

> 用户原话：**「先修复一个东西。我现在无法彻底退出dsh，从托盘退出也不行」**

---

## 1. 现场（先量，不猜）

用户报这个的时候，机器上是这样的：

| 观测 | 值 | 怎么测的 |
|---|---|---|
| 端口 3105 的持有者 | **pid 9724** | `netstat -ano \| findstr :3105` |
| 9724 是什么 | **内核**：`"…\Programs\DSH Integrated\DSH Integrated.exe" --expose-internals …\@deepseek-ai\dsh\lib\bin.js web --host 127.0.0.1 --port 3105 --no-open` | `Get-CimInstance Win32_Process` |
| 9724 的父进程 | **12160 —— 不存在了** | 同上（父 pid 在进程表里查不到） |
| 9724 的启动日志 | **不存在**：`<userData>\logs\` 里 00:34:07 只留下一个**崩溃**日志（`…-724Z.err.log`，5007 B，EADDRINUSE） | `Get-ChildItem $env:APPDATA\'DSH Integrated'\logs` |
| 外壳的记录文件 | **`kernel.json` 不存在** | `Test-Path` |
| 外壳怎么看它 | `复用已有内核（裸 origin，dsh-auth）` ⇒ `serverOwned = false` | `shell.log` |

**结论：外壳退了，但它复用的那个内核还活着、还占着 3105。**
下次启动又把这个内核复用回来 ⇒ 同一个会话、同一个状态 ——
在用户看来就是"根本没退"。任务管理器里 `DSH Integrated.exe` 也还在
（内核用的就是同一个 exe：`spawnKernel` 拿 `process.execPath` 配
`ELECTRON_RUN_AS_NODE=1` 当 node 用，`src/kernel.js`）。

### 这条链断在哪（三处，互相咬死）

```js
// ① 复用时只把"不是我起的"记在心里，没别的动作
serverOwned = false;                       // main.js ensureServer ①a / ①b

// ② 退出时只关"我 spawn 的那个"
if (kernelProc && serverOwned) K.killTree(kernelProc);   // before-quit

// ③ 而"重启内核"在复用状态下**永远失败**
stopOwnedKernel();                         // 什么都没杀
await ensureServer({ profile, reuse: false });   // ⇒ ③ 端口被占 ⇒ 抛错
```

于是形成**单向门**：一旦走到「复用」，就再也回不到「拥有」——
端口永远被那个内核占着，而外壳永远不敢关它。
用户在界面上点「重启内核」也救不回来：`shell.log` 里连着三次
`重启到档案 web 失败: 端口 3105 已被占用，但上面探测到的不是 dsh 服务`
——**这句话本身就是错的**：探活明明认出上面就是 dsh（`dsh-auth`）。

### `kernel.json` 为什么会不见

`stopOwnedKernel()` 以前**无条件** `clearKernelRecord()`。
在"复用"状态下点一次「重启内核」（或任何调它的路径），
它什么都没杀，却把记录抹掉了 ⇒ 此后永远退回裸 origin、
永远认不出这个内核是自己人。这就是用户现场那条链的起点。

### 那个孤儿内核是怎么来的（未完全定论，但证据指向"内核自身的脱离式重启"）

第一反应是"外壳被强杀、内核没死"。**实测走不通**：本机
`taskkill /F` 掉外壳之后，它 spawn 的内核**也一起没了**（job 对象）。
这一点与 `scripts/ui-check.js:649-657` 早在 2026-09-20 就记录过的实测一致
（"强杀客户端后复用残留内核这个场景在本机根本不可达"）。

但孤儿内核确实存在，而且三条证据同时指向它**不是外壳这一次 spawn 出来的**：

1. 它没有 `spawnKernel` 必然创建的日志文件（那一对 `kernel-*.log` 不存在）；
2. 它的父进程已经死了；
3. 它的 argv 与 `spawnKernel` 造出来的**一字不差**
   （`--expose-internals <bin.js> web --host … --port … --no-open`）。

⇒ 最合理的解释：**内核（它自己也是 `DSH Integrated.exe` + `ELECTRON_RUN_AS_NODE`）
以 detached 方式重启了一次自己**（脱离 job ⇒ 父进程死了它还活），
而外壳仍以为自己在跟旧的那个说话。**这一点没有定论，不影响修复**：
修复针对的是**状态**（端口上有一个本应用拉起来、却没人负责关的内核），不是它的来源。

## 2. 改了什么

原则一句话：**能证明"这个内核是本应用拉起来的"，就认领它、退出时关掉它；
证明不了（例如用户自己在终端里 `dsh web` 起的），一个字都不动。**

| # | 位置 | 改动 |
|---|---|---|
| 1 | `src/kernel.js` 新增 `portOwner(port)` | `netstat -ano` 读出端口持有者 pid |
| 2 | `src/kernel.js` 新增 `waitPortFree(port)` | 杀完内核要**等端口真的放开**再起新的 —— 不等就撞 `listen EADDRINUSE`（本机实测过：旧内核 00:34:07 退出、新内核 00:34:07.7 起来，当场崩在 webserver） |
| 3 | `src/kernel.js` 新增 `processInfo(pid)` / `ourKernelProcess(pid, port)` | 判"是不是本应用拉起来的内核"，**四条 ASCII 判据**：文件名一致 + `--expose-internals` + `lib/bin.js` + 同一个端口 |
| 4 | `src/main.js` `claimAdoptedKernel()` | 复用（①a / ①b）时认领；**父进程还活着就不认领**（那是别的外壳实例正在用的内核） |
| 5 | `src/main.js` `shutdownKernels()` | 退出时关：**自己 spawn 的 + 认领来的**；`finishSmoke` 也调它（`app.exit()` 会跳过 `before-quit`） |
| 6 | `src/main.js` `quitApp(reason)` | 退出收敛到**一个函数**：托盘、安装包、验收脚本走的都是它；并且**写日志**（以前退出这条路一行日志都没有，出了事无从查起） |
| 7 | `src/main.js` `stopOwnedKernel({adopted})` | 「重启内核」连认领的一起停；**记录只在真动了那个 pid 时才清**（补上那条单向门） |
| 8 | `src/main.js` `restartKernel` | 停完**等端口放开**再起；`handleServerDown` 里清掉失效的认领 |
| 9 | `src/main.js` 端口占用报错 | **先探活再下结论**：上面是 dsh 就照实说（"已经有一个 dsh 内核在跑，pid …"），不再把"已经在跑的 dsh"误报成"别的程序占端口" |
| 10 | `src/main.js` 托盘「关于」 | 新增一行「内核归属」：本应用启动 / 认领来的 pid / **不是本应用启动的（退出时不动它）** |
| 11 | `src/main.js` `armQuitOnFileHook()` | **只给验收用**的退出开关：`!app.isPackaged` + 必须显式给 `DSH_QUIT_ON_FILE` ⇒ **打包版里等于不存在** |
| 12 | `src/kernel.js` `spawnKernel({detached})` | 默认 `false`（正常路径不变）；验收脚本靠它造出"孤儿内核"现场 |
| 13 | `src/main.js` `handleServerDown` | 杀掉自己的内核后**等端口放开**再恢复；清掉已失效的认领（否则可能拿一个被系统复用了的 pid 去杀别的进程） |
| 14 | `src/main.js` `finishSmoke` | 调 `shutdownKernels({ adopted: false })` —— 冒烟是**自检**，不许把用户正在用的客户端弄停（见 §6） |

### ★★ 一个只有真跑才会暴露的坑（第一版修复**完全无效**）

`ourKernelProcess` 第一版是拿**完整路径逐字节比**：

```js
if (exe.toLowerCase() !== String(process.execPath).toLowerCase()) → 不认领
```

验收直接 FAIL —— 一次都认领不到。根因：**WMI 的 `CommandLine` 经 PowerShell
往返之后，路径里的中文段会被改掉**（本机控制台里 `5.DSH集成桌面端` 一直显示成乱码）。
判据因此**永远为假**。
⇒ 改成只比 **ASCII 片段**（文件名 + `--expose-internals` + `lib/bin.js` + 端口）。
**教训：跨 PowerShell 边界的字符串判据，不要依赖非 ASCII 内容。**

### ★ 四条判据逐条对得上用户那个真实内核

拿现场那个 pid 9724 的真实命令行去核（这是"装上新版本就能治好"的硬依据）：

```
"C:\Users\24239\AppData\Local\Programs\DSH Integrated\DSH Integrated.exe"
  --expose-internals C:\Users\24239\AppData\Roaming\npm\node_modules\@deepseek-ai\dsh\lib\bin.js
  web --host 127.0.0.1 --port 3105 --no-open
```

| 判据 | 现场值 | 命中 |
|---|---|---|
| 文件名等于本外壳的可执行文件 | `DSH Integrated.exe` = 外壳自己的 exe | ✅ |
| 含 `--expose-internals` | 有 | ✅ |
| 含 `lib/bin.js` | `…\@deepseek-ai\dsh\lib\bin.js` | ✅ |
| `--port` 等于当前端口 | `--port 3105` | ✅ |
| 父进程还活着？（活着就不认领） | 父进程 12160 **已不在** | ✅ |

⇒ 修好的外壳启动后会**认领**它，退出时把它一起关掉。
**而用户在终端里自己起的那个（命令行是 `node.exe`）四条里第一条就不命中 ⇒ 一个字都不动。**

### ★ 认领要查 WMI，所以它**不许挡住启动**

PowerShell 冷启动要几百毫秒，而且是同步查的话会**卡住主进程**。
⇒ `processInfo` 用 `execFile` **异步**拿结果，`claimAdoptedKernel` 是 `async`，
调用方一律 `void claimAdoptedKernel(...)` 发出去就走 —— UI 该多快还多快，
认领结果几百毫秒后落到 `adoptedKernelPid`。

（第一版是同步 `spawnSync`：虽然验收也能过，但它把几百毫秒塞进了启动关键路径。
改异步之后又踩了一个 `node --check` **看不出来**的错 —— 忘了把 `execFile` 加进
`require` ⇒ 运行期 `ReferenceError: execFile is not defined`。
**"真加载一次"这个习惯又救了一次**；`node --check` 只查语法，不查标识符是否存在。）

## 3. 验收：`npm run quit:check`（新增，13 项断言 × 2 个现场）

以前**退出这条路一条断言都没有**（`npm run` 里根本没这项），所以它坏了整整几天没人发现。

```powershell
npm.cmd run quit:check                      # 两个现场都跑（约 3 分钟）
node scripts/quit-check.js --mode=norecord  # 只跑用户现场
node scripts/quit-check.js --keep           # 保留临时目录便于翻日志
```

**两个现场**（全程临时 userData + 临时 DSH_HOME，**不碰 B、不碰 A、不碰 3105**）：

* `record`：端口上有个孤儿内核，且 `<userData>\kernel.json` 在 ⇒ 走 ①a（带记录复用）
* `norecord`：孤儿内核在，但记录**丢了** ⇒ 走 ①b（裸 origin 复用）—— **用户现场**

**怎么做出来的**：孤儿内核不能靠"强杀外壳"复现（见上文），
所以由 `scripts/quit-orphan.js` 用一个**一次性父进程**以 `detached: true`
把内核起起来、拿到就绪信号后自己走人 ⇒ 得到一个父进程已死、
仍在端口上服务的内核（与用户现场状态一致）。

**怎么触发退出**：写一个标记文件，外壳的 `armQuitOnFileHook()` 看到就调
`quitApp()` —— **与托盘那条「退出」是同一个函数**。
（第一版走 CDP 连主进程调 `app.quit()`，实测返回 `NO_LOADER`：
`require` / `process.mainModule` / `module` 在主进程 inspector 上下文里都不存在。那条路已废弃。）

## 4. 交付这个修复要重装客户端

外壳代码是**打进安装目录**的（`app.asar`）——

> 「用户重启了还是看不到」要先问「他跑的到底是哪个构建」。
> —— 本项目 AGENTS.md §8 的第 3 条教训

所以：**光重启客户端不会生效，必须装一个新版本**（0.2.10）。

### 在装新版本之前，用户当场就能自救（0.2.9 也管用）

那个孤儿内核杀掉之后，**当前这个外壳的健康检查会立刻自己拉起一个新内核，
并且这次是它自己启动的 ⇒ 它拥有它 ⇒ 之后托盘「退出」就能退干净了。**

```powershell
taskkill /pid 9724 /T /F
```

自救的原理（0.2.9 的代码就能走通）：健康检查每 **5 秒**探一次、连续 **3 次**失败
（`HEALTH_INTERVAL = 5000` / `HEALTH_FAIL_LIMIT = 3`，`src/main.js:1320-1322`）就调
`handleServerDown()` ⇒ `ensureServer()`：记录没了、端口空了 ⇒ 走到 ④ **自己起一个**
（`serverOwned = true`）⇒ 0.2.9 原有的 `before-quit` 就会关它。
**大约 30–60 秒后界面自己恢复。**

⚠️ 两个提醒：
1. 这条命令会**杀掉本会话正在跑的内核** —— 也就是说，正在进行的这次对话会中断
   （会话记录是持久的，重启客户端后还能打开）。
2. 它是**用户自己执行**的操作，不是 AI 执行的：AI 跑在这条链上游，
   杀了它等于把自己连同"用户还能提问"一起杀掉（本项目红线第一条）。

## 6. ⚠️ 给自己人的三条警告（都是这次实测出来的）

### ① 别在会话里跑 `npm run smoke`（会杀掉正在用的内核）

`npm run smoke` = `electron . --smoke`，用的是**真实 userData**。
它会认领用户此刻正在用的那个内核，而冒烟收尾会调 `shutdownKernels()` ——
**等于把正在跑的客户端弄停**（AI 自己就跑在那个内核里，这一下会把自己也带走）。

⇒ 已加闸：`finishSmoke()` 调的是 `shutdownKernels({ adopted: false })`
—— **冒烟是自检，只关自己 spawn 的那个，认领来的一律放过。**

同理：**任何开发态的 `electron .` 都必须带 `--user-data-dir=<临时目录>`**，
否则它会连上真实内核、并（在修好之后）有权关掉它。

### ② `ui-check.js inject` 模式不要在本会话里跑

它刻意用**真实端口 3105**（复用用户正在跑的内核）。虽然它的 `stopApp()` 走的是
`child.kill()`（Windows 上是 `TerminateProcess`，**不触发 `before-quit`**）
所以本会话实测是安全的，但这条安全完全依赖"不走优雅退出"这个细节 ——
不值得去赌。

### ③ 既有失败（与本次改动无关，已 A/B 核对）

| 检查 | 结果 | 是否本次引入 |
|---|---|---|
| `ui-check.js reuse` B 三条 | 假 FAIL（固定 `sleep(4000)` 太紧，本机内核 7 秒就绪时正好错过页面切换） | **否**：HEAD 版本同样 3 FAIL。已把判据改成**轮询** |
| `ui-check.js loading` 两条 | FAIL（内核 7 秒就绪 ⇒ 状态页被顶掉 ⇒ 体检输出读不到、"不是外壳自有页面"拒绝） | **否**：HEAD 版本同样 2 FAIL |

A/B 做法：把我的 `src/main.js` / `src/kernel.js` 备份后用
`git checkout HEAD -- src/main.js src/kernel.js` 换成基线版，
各跑一次，再逐字节还原（`main 一致 = True  kernel 一致 = True`）。
**这是唯一能分清"我改坏了"与"本来就坏"的办法。**
