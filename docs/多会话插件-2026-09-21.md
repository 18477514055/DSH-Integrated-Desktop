# 多会话插件：一图流记录（2026-09-21）

> 一句话：**在主输入框旁边加了一个「多会话」按钮，点开是个大弹窗，里面可以并排放 N 个输入框，
> 右下角一键发送 —— 一次建 N 个会话，N 条提示词分别发出去，并行跑。**
>
> 能力表、装法、边界见 `plugin/dsh-multi-session/README.md`；本文只记**过程**：
> 为什么这么设计、怎么验证的、踩了什么坑、留下了什么没做。

---

## 一、需求原话与它带来的第一个结论

> 「点击之后弹出一个大弹窗。允许同时创建多个会话（默认一个，加数量时点一下"新增会话"）。
> 弹窗由主界面的这个主输入框的多个（具有除了发送以外的所有功能）构成，弹窗右下角一键发送。」

"由主输入框的**多个**构成"这句直接指向一个必须先回答的问题：**官方那个输入框能不能被复用 N 次？**

**答案是不能，四条独立证据，每条都足以致命**（详细出处与原文见插件 README）：

1. 它是 `kind:'single'`、`scope:'session-maybe'` 的**单例槽位**；
2. 它的会话来自 React context 的"当前绑定"，渲染路径上**没有覆盖点**；
3. 插件**不能渲染**那个槽位（`SlotOwnershipError`），也不能替换 scope 适配器（重复注册抛错）；
4. 输入框组件与它的 Lexical 编辑器**既不导出也不可 require**，连 `lexical` 都不在平台共享模块表里
   （那张表只有 9 个词：`react` / `react/jsx-runtime` / `react-dom` / `react-dom/client` /
   `@deepseek-ai/cordis` / `dsh-client-store` / `dsh-client-ui-slots` /
   `dsh-client-ui-primitives` / `dsh-client-ui-dockkit`）。

⇒ 唯一可行路径是**部分重实现**：文本面自己写，**语义尽量借官方的**。

于是问用户"要做到哪一档"，用户选了**全功能档**（含 `/` 命令与 `@` 文件引用），
按钮位置选了**主输入框右侧、发送键旁边**。

---

## 二、做成了什么

一个**客户端插件**（官方 Web 前端的浏览器半边插件），**零 npm 依赖**，**无构建步骤**（手写 bundle）。

```
plugin/dsh-multi-session/
  package.json          dsh.bundle.patch + dsh.client.inject + platform:web
  cordis.patch.yml      insert 自己这一行 —— **缺它内核直接拒绝加载**
  lib/index.js          宿主半边：空 apply()（纯浏览器能力）
  lib/client.js         浏览器半边：全部实现（约 800 行，带逐条出处注释）
  README.md             能力表 / 架构依据 / 装验退 / 踩过的坑
```

注册的槽位（官方 61 个槽位里挑的两个，都是**叠加型**、`replaceRisk: none`）：

| 槽位 | 作用 | 为什么选它 |
|---|---|---|
| `conversation.input.right` | 触发按钮 | 官方描述："发送键之前的紧凑控件" |
| `shell.overlay` | 大弹窗 | 官方描述："全帧浮动层……**新 id 是叠加而非替换**" |

每行输入框的能力（**全部在临时环境里真跑验证过**）：

| 能力 | 借的官方接口 | 关键依据 |
|---|---|---|
| 多行文本 | 自己的 textarea | 官方编辑器不可达 |
| 模型选择（每行各自） | `ctx.remote.session.modelCatalog()` | **不需要 sessionId** |
| `/` 命令 | `ctx.remote.commands.list(sessionId)` | 位置参数、必填 sessionId |
| `@` 引用 | `ctx.remote.fileReferences.list(sessionId, query)` | 同上；提及语法照抄官方 |
| 附件 | `ctx.conversation.createDrafts` + `sendSession` | 官方完整提交管线 |
| 工作区（每行各自） | 标准 prop `useWorkspaces` + `create({workspaceId})` | 字段是 `workspaceId`/`title` |

**发送走官方完整路径**：建会话 → （选了模型才）`selectModel` → `createDrafts` →
等后台上传完成 → `sendSession(face, text, ids, "queue")`；
拿不到就退回 `prompt()` 并**在结果里写明走了哪条路**。

**一个刻意的设计决定**：`sessions` 命名空间**没有 delete**。
所以**绝不在用户没决定发送时就建会话** —— 否则一取消就在侧栏留下删不掉的空会话。
代价是 `/` 与 `@` 只能借"打开弹窗那一刻的当前会话"作作用域（默认同工作区，候选是对的）。

## 三、怎么验证的（**这是本次最该被复用的部分**）

新增 `scripts/plugin-check.js`：搭一套**临时环境**真跑，**三层证据，后两层刻意不看插件自己的报告**。

临时环境（全部不碰 B / A）：

```
runtime/plugin-check/<时间戳>/userdata/          ← Electron --user-data-dir
  settings.json                                   ← 空闲端口 3179 / closeToTray:false
  dsh-home/                                       ← 外壳的 DSH_HOME = userData/dsh-home
    storages/workspace.json                       ← 从 B 拷来（只有路径，没有凭据）
    profiles/
      node_modules/   ← 【目录联接】B 的（只读借用内核依赖树）
      web/
        cordis.yml    ← []
        package.json  ← bundles = dsh-base + dsh-web-app + 本插件
        node_modules/dsh-multi-session/ ← 【目录联接】本仓库的 plugin 目录
```

用**联接**而不是拷贝/安装：零网络、零解析、零构建，且**跑的就是仓库里那份源码**。

★ `plugin-check` **默认把用户真实环境的 bundle 清单整个镜像过来**：第三方插件（`dsh-qoder-connect`
/ `dsh-connect-workbuddy` / `dsh-plugin-install` / `dsh-whale-widget` / `@dsh-pet/bridge`）
逐个从真实 `profiles/web/node_modules` 目录联接过来，连真实 profile 的 `cordis.patch.yml`
补丁层（它 disable 了 `dsh-crosshub`）也一起带上 —— 否则"配置不等价"，验证结论就打了折扣。
最终跑的就是**用户实际那套 9 个 bundle**（57 条启动图 entries、模型下拉 42 项）。
加 `--minimal` 才退回 `dsh-base + dsh-web-app` 的最小界面。

三层证据：

1. **结构**：`window.__DSH_BOOT__.entries` 里有 `dsh-multi-session` ⇒ 宿主真的把它公告进了启动图。
2. **动态**：页面里出现插件注入的 `<style data-plugin-css>` ⇒ **`apply()` 真的跑了**。
   ★ 这一层才排除假阳性 —— "bundle 被下载了"不等于"插件挂上了"。
3. **端到端 + 交叉核对**：点「一键发送」之后，**不信插件的结果文案**，去**临时 DSH_HOME 的磁盘**上找：
   - `sessions/` 下有没有新会话；
   - **整盘搜索我输入的那两串标记文本**；
   - 附件字节在不在 `attachments/v1/files/…` 下。

最终结果（原文）：

## 八、第二轮：模型搜索/筛选，以及一个会让按钮永久卡死的真 bug

用户看到按钮后追加：**「为那个位置的模型选择加上我们的搜索框和筛选标签」**，
并拍板了一条落点原则与一件后续（已记进项目 `AGENTS.md` §1/§2）：

> 「以后我们的这些功能，**能放进来就放进来，放不进来就插件**。」
> 「这些插件后面我们做一个列表，可以显示在主界面中查看**来自我们这个包的插件**。」

### 8.1 做了什么

模型下拉从"42 项平铺"变成：**搜索框 + 按来源分组 + 来源筛选胶囊**。
语义**照抄** `src/inject/model-search.js`（那是给官方「选择模型」菜单做的那套），
逐条对齐：关键词命中提供方名则整组显示、胶囊再点一次取消、胶囊只在提供方多于一个时出现、
数字是该提供方全部条数、空态文案与「清空搜索与筛选」。
唯一差异写在明处：匹配面多了 `description`，所以略宽松。

真实数据实测：**42 个模型 / 4 颗胶囊**
（`全部 41 · deepseek-official 4 · workbuddy 16 · workbuddy-global 21`），
搜 `deepse` → 42 → **9 条且条条命中**；点 `deepseek-official 4` → 恰好剩 4 个。

### 8.2 顺手抓到并修掉的两个真 bug（都是"会丢用户东西"级别）

**① 按 Esc 会丢掉整个弹窗的草稿。**
`primitives.Modal` 内部**自己在 `document` 上挂了 Escape → `onClose`**。
我传的 `onClose` 是关弹窗，于是"在搜索框里按 Esc"会沿着冒泡走到那个监听上，
**把整个弹窗关掉、N 条已写好的提示词一起没了**。
⇒ 不再用官方 `Modal` 包最外层（自己的遮罩本来就是 `fixed + z-index:9999`，覆盖不受影响），
Esc 完全自己控制，并做成**三级**：清搜索词 → 清来源筛选 → 才关下拉；**弹窗不因此关闭**。

**② 发送键会永久卡在「发送中…」（最严重的一个）。**
用 `conversation.sendSession` 提交**带附件**的内容时，它的 promise **可能永不结算**：
带附件时它会 `await` 乐观回显的"退休"（等持久事件或队列行），
而本插件的会话是刚建出来、**没有被跟随**（没有 live 事件流订阅）。
实测症状极具欺骗性：**界面永远在"发送中…"，而宿主其实早就受理并落盘了**
（磁盘上找得到提示词与附件字节）。

发现过程值得记下来，因为中间**被自己的诊断误导过一次**：
4 连跑里出现"1.5 秒成功 / 180 秒不出现"，第二类的 store 快照显示
`notice:"正在等附件上传完成（还有 1 个）…"` ⇒ 我以为是附件上传等待卡住。
但**同一份磁盘证据显示带附件那条的提示词已经落盘** —— 如果还卡在"等上传"，
`sendSession` 根本不会被调用，提示词也就不可能落盘。**两条证据互相矛盾 ⇒ 说明 notice 是假的。**
真因是：`notice` 在我这套代码里**从不清除**，所以它残留着上一阶段的字符串。
加上 `diagnostics.sends` 打出 `done:false` 之后才定位到"Promise.all 没回来"。

修法：改用**完成语义有界**的路径 —— 自己把附件传成 wire parts
（图片 base64；其它文件 `fileUpload.upload` 换 `receiptId`），再 `face.prompt(parts,'queue')`
（官方文档：返回值是 "Receipt after one prompt enters the target Agent inbox"，只等到受理）。
代价是失去乐观回显，换来**不会卡死**。同时给 `sendAll` 加了兜底 try/catch，
并把 `notice` 在结果出来后清掉（就是它误导了我）。

### 8.3 稳定性证据（**flaky 必须跑到稳**）

修完后 **连跑 4 次全过**，发送耗时 1.5–3.3 秒。
另有一轮 4 连跑里出现过 1 次 FAIL，查明是**验证脚本自己的时序问题**
（页面已加载但 composer 槽位还没渲染完，脚本用固定 `sleep(4000)` 就去找按钮）⇒
已改成**轮询等按钮出现**（45 秒上限），之后 4 连跑全过。

### 8.4 这一轮新增的坑（已进项目 `AGENTS.md` §3 那张表）

| 坑 | 教训 |
|---|---|
| `primitives.Modal` 的 Escape 监听从内部关掉整个弹窗 | 用官方组件前先确认它**自己挂了哪些全局监听** |
| `sendSession` 在有附件时可能永不结算 | "能调用"≠"能依赖"；提交路径要选**完成语义有界**的 |
| 诊断字段从不清除 ⇒ 残留字符串 | 诊断输出必须能跟"当前这一刻"对上，否则**会把人引偏**（这次真的发生了） |
| 验证脚本用固定 sleep | 等**条件**，不要等**时间** |

## 四、五个真坑（都是"看起来完美"的那种）

| # | 坑 | 表现 | 怎么发现的 |
|---|---|---|---|
| 1 | 插件包只写 `dsh.client`，不写 `dsh.bundle.patch` | 内核**直接拒绝启动整个 profile**：`Error: dsh: profile bundle "dsh-multi-session" declares no dsh.bundle in its package.json` | `plugin-check` 第一次跑就抓到 |
| 2 | `onClick` 里用了函数作用域里并不存在的 `ctx` | **按钮在、点了没反应、控制台什么都不说**（ReferenceError 被事件回调吞掉） | 加"点击计数 + onClick 内 catch 记录"后抓到，原文 `trigger onClick: ctx is not defined` |
| 3 | 继承了槽位 owner 传来的 `disabled` | 当前会话忙碌时按钮变灰、点不动 —— 而那恰恰是最想用它的时候 | 同上（诊断里 `disabled` 一次都没打印过，因为第一版直接吃掉了） |
| 4 | 不等附件后台上传完成就 `sendSession` | `conversation.sendSession: one or more files have not finished uploading`（官方是靠在 UI 上禁用发送键规避的，本插件"一键发 N 行"不能禁用，只能等） | 把 `createDrafts` 与 `sendSession` **分开归因**后拿到完整原文 |
| 5 | `.gitignore` 的白名单没放行 `!/plugin/`，且兜底的 `**/cordis.patch.yml` 会把插件自带的补丁排除掉 | 提交出去的是**坏的插件**（clone 下来内核拒绝加载） | `git ls-files --others --exclude-standard plugin/` 逐条核对，并在 `.gitignore` 里写了带原因的例外 |

另外**顺带修好的两处自己写的错**：模型目录的形状（官方是 `groups[].models[]`，第一版按
`providers[]` 猜）、以及命令/引用接口的参数形状（都是**位置参数**，第一版按对象传）。

## 五、边界（别把这些说成"和官方 1:1"）

- 文本面是 `<textarea>`，**不是**官方 Lexical 富文本：没有引用 chip 的原子节点、没有装饰器。
- `/` 与 `@` 菜单是本插件自己弹的（官方 `MenuView` 没导出，且它的 `pick` 会把事件派进官方编辑器）。
- 行内 **Enter 是换行**，`Ctrl/Cmd+Enter` = 一键发送（刻意如此：避免"某一行偷偷先跑"）。
- 没有权限预设 / Agent 预设 / Plan 模式。
- 附件只支持回形针选取，**拖入与粘贴还没接**。
- `/` 与 `@` 的候选作用域 = 打开弹窗那一刻的当前会话。
