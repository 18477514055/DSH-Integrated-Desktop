# DSH 集成桌面端 0.2.11

把官方 DeepSeek Harness 内核装进原生 Electron 外壳。**外壳不修改内核的任何文件**；
内核由外部独立安装与升级 —— 升级内核不需要动外壳。

> 这一版就一件事：**「检查更新」要能看见本机已经打好的包**。
> 用户原话：「为什么我点检查更新的时候找不到你打包的 0.2.10 呢？这个查找工具是不是也有点问题？」

> ⚠️ **必须重装一次**（不是"重启客户端"）：外壳代码是打进安装目录的，重启不会换代码。

## 一、结论先说：查线上没错，**扫本机那半坏了**

用户的怀疑一半对一半不对，先把两半分开：

| 那一半 | 判定 | 证据 |
|---|---|---|
| **查线上** | ✅ **没错** | 真连 `api.github.com/repos/18477514055/DSH-Integrated-Desktop/releases/latest`，HTTP 200；**全部** Release 里确实没有 `v0.2.10`，`latest` 就是 **`v0.2.9`**（发布于 2026-09-22T18:48Z）。用户当时装的正是 0.2.9 ⇒ 报「已是最新」是**正确**的 |
| **扫本机** | ❌ **坏了** | 打好的 0.2.10 就躺在 `D:\deepseek-workspace\5.DSH集成桌面端\release\`，而候选目录里**一个都没覆盖到它** |

**0.2.10 从没发布过**（`release:bundle` 要求工作区干净，而那几天另一个会话一直在同一个
仓库里改）—— 所以线上没有它是正常的；不正常的是**本机明明有、却扫不到**。

## 二、根因：清单问的是"用户配了什么"，而不是"包会落在哪"

旧实现（`src/main.js` 的 `localInstallerDirs()`）：

```js
const dirs = [app.getPath("temp")];
if (settings && settings.workspace) dirs.push(path.join(settings.workspace, "release"));
```

两个问题叠在一起：

1. **`settings.workspace` 的语义不对** —— 它是**内核的工作目录（cwd）**，不是"安装包放哪"；
2. **用户现场它是空串** —— 实测 `%APPDATA%\DSH Integrated\settings.json` 里 `workspace=''`
   ⇒ 那个 `if` **永远不成立** ⇒ 候选目录只剩临时目录一个。

★ 最讽刺的是 `findLocalInstaller` 的注释写的**正是为了这个场景**
（「自己 `npm run dist` 打出了新版本，但因为工作区不干净一直没发到 GitHub ⇒
线上还停在旧版本，只查线上就永远报『已是最新』」）——
**它的理由是对的，输入是空的。** 一个功能写对了目的、却永远拿不到数据。

## 三、修法：清单由「包实际会落在哪」推导

新增 `src/update.js` 的 **`candidateInstallerDirs()`**，四个来源：

| # | 来源 | 为什么 |
|---|---|---|
| ① | 下载临时目录 | 更新流程自己下过的 |
| ② | `settings.workspace\release` | 保留旧行为 |
| ③ | **外壳项目目录 `\release`** | 开发机 `npm run dist` 的产物就在这儿（**0.2.10 的所在**） |
| ④ | **每个已注册工作区**：根 + **一层子目录** + `release` | 本机实况：工作区根 `D:\deepseek-workspace`，项目在它子目录 `5.DSH集成桌面端` 下 |

★ 扫子目录时**必须跟随联接（Junction）** —— `Dirent.isDirectory()` 对联接返回 **false**，
不跟随就会整批静默跳过（项目 §7 记过这个坑）。结果去重。

★ 打包版注意：`app.getAppPath()` 在打包版里是 `<安装目录>\resources\app.asar`
⇒ `join(appPath,'release')` 那个候选**在打包版里不存在**（无害，会被跳过）。
打包版真正管用的是 ④ —— 实测它推出的 `D:\deepseek-workspace\5.DSH集成桌面端\release`
正是用户那个 0.2.10 的所在。

## 四、顺带治本：**让"没找到"变得可解释**

这个 bug 能藏那么久，是因为界面只报一句「已是最新」，**没人知道它扫过哪里**。

* `check()` 现在返回 **`scannedDirs`**（每个目录 + 它是否真的存在）；
* 设置页「更新」栏多一行 **「扫过的本机目录」**，逐条标 `[有]` / `[无]`；
* 同时写进 `shell.log`：`检查更新：扫了 N 个本机目录（M 个存在）：…`。

⇒ 以后「没找到」是可解释的。**凡"搜了一圈没找到"的功能，都要把搜索范围报出来。**

## 五、验收（真跑，不看自述）

| 检查 | 结果 |
|---|---|
| `npm run update:check` | 全绿 `EXIT=0`。推导出 **11** 个候选目录，其中 `[存在] D:\deepseek-workspace\5.DSH集成桌面端\release`；以 v0.2.9 为基准**真的扫到 v0.2.10**（正是用户现场扫不到的那个）。另补 **7 条** `candidateInstallerDirs` 断言（含联接跟随、去重） |
| `node scripts/ui-check.js pages` | **「pages 模式全部通过」`EXIT=0`**。★ 走的是**真实 `main.js` 接线 + 真实设置页 DOM**（不是直接调函数）：**45** 个候选目录 / **3** 个存在，清单里真有本仓库 `release\`，每条都标了 `[有]/[无]` |
| `npm run quit:check` | 仍 **26 PASS / 0 FAIL** —— 确认这一版没碰坏 0.2.10 的内核收尾 |

★ **探针过了 ≠ 接线对了**：`update:check` 是直接调 `candidateInstallerDirs()`，
所以必须再由 `ui-check pages` 从**真实 IPC 路径**上再钉一遍 —— 这一版两条都做了。

★ 修的时候自己又踩了一次「**尺子错**」：新加的断言复用了上一个**假清单**的 `has()`，
于是真清单明明是对的却报 FAIL —— 改成 `hasReal()` 才对。
**先证明尺子对，再报结论。**

## 六、给自己人的两条提醒

1. **同版本不算「有更新」**（`cmpVersion(ver, current) <= 0` 就跳过）——
   所以**修完 bug 必须升版本号**，否则本机那个包永远不会被提示，
   用户只能靠"自己知道路径"去手动装。这一版就是因此从 0.2.10 升到 **0.2.11**。
2. **`release:bundle` 仍然要求工作区干净**。本机长期有另一个会话在同一仓库里干活
   ⇒ 出包前先 `git status`，**永远不要 `git add -A`**，显式列自己的文件。
