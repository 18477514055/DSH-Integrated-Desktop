# DSH 集成桌面端 0.2.7

把官方 DeepSeek Harness 内核装进原生 Electron 外壳。**外壳不修改内核的任何文件**；
内核由外部独立安装与升级 —— 升级内核不需要动外壳。

> 这一版修的是一条**用户真实撞上的** bug：
> 「最开始的时候可以看到开放平台，但是现在点到开放平台，它还是保持着网页版的状态。」

## 一、真因：两个网站**共用一个视图层**，而失败是静默的

0.2.6 及以前，`src/sites.js` 里只有一个 `WebContentsView`，网页版与开放平台**轮流用它**。
于是四件事叠在一起：

| # | 原来的写法 | 造成的后果 |
|---|---|---|
| 1 | `let view = null`，共用 | 平台加载失败时，屏幕上留着的是**上一个站点的页面**（网页版） |
| 2 | 失败只写一行 `shell.log` | 界面上**完全看不出来** |
| 3 | `activeId` 无条件设成目标页 | 面板的 ✓、推给按钮的状态、托盘勾选**全都说你在开放平台** |
| 4 | 「已加载就不重载」拿 `wc.getURL()` 当判据 | 失败后地址仍停在 chat ⇒ **点哪一页都不重载**，看着就是卡住 |

**用户日志里的原始证据**（`%APPDATA%\DSH Integrated\shell.log`）：

```
18:38:50  加载站点：https://platform.deepseek.com/   切到页面：DeepSeek 开放平台
18:38:53  站点加载失败（继续显示，用户可重试）: ERR_ABORTED (-3) loading 'https://platform.deepseek.com/'
18:38:56  站点加载失败（继续显示，用户可重试）: ERR_ABORTED (-3) loading 'https://platform.deepseek.com/'
18:38:58  切到页面：DeepSeek 网页版                 ← ★ 这一条前面**没有**"加载站点"
18:38:59  加载站点：https://platform.deepseek.com/   切到页面：DeepSeek 开放平台
```

第 3 行是关键：切「网页版」时**没有重新加载**，说明那一刻共用那个 view 的地址**已经是
chat.deepseek.com** —— 屏幕上是网页版，状态却说你在开放平台。18:38:50 那次还是好的，
从 :53 起每次都是 `ERR_ABORTED`（**站点侧原因**，见第三节）。

## 二、修法：一页一个视图 + 状态不许撒谎

### 1. 每个网站**各有一个自己的 `WebContentsView`**

`states: Map<id, {view, url, error, …}>`。切到哪一页就只让**那一页的**视图可见
（其余 `setVisible(false)`），本机 DSH 仍然只是"全部隐藏"（它就是主窗口自己的 webContents）。
⇒ 一页加载失败**不可能**再让另一页的页面留在屏幕上。

### 2. "要不要重新加载"换判据

只有两种情况才重新加载：**① 这一页从来没提交成功过**；**② 上一次尝试以失败告终**。
刻意**不**再用"当前地址和想去的地址同不同源" —— 那个判据在失败时会拿到
**上一个站点的地址**，正是死循环的来源。

### 3. 失败必须**看得见**

* 主框架**没提交成功**（`did-fail-load`）⇒ 把**那一页自己的**视图换成一张
  **本地错误卡片**（`data:` 页，不依赖网络）：错误码 + 想打开的地址 +
  「在右侧 ⇄ 面板里再点一次这一页就会重试」+ 一句「若是 HTTP 429 / 请求被拒绝，
  多半是站点临时挡住了你这台机器/这条线路」。
* 主框架**提交成功但返回 4xx/5xx** ⇒ **不动**站点的页面（它自己的说明往往更有用），
  但在面板那一行小字里标出「站点返回 HTTP 429（页面照常显示）」。
* 主框架**提交成功却停在别的域**（被重定向，例如要求先登录）⇒ 面板标出「实际停在 xxx」。
  **不拦重定向**（拦了会弄坏登录流程），但**必须说出来**。

> ★ `ERR_ABORTED (-3)` 有**两种**来源：① 被后面那次导航顶掉（WAF 挑战脚本、
> 登录跳转、`location.replace` 都会这样）；② 真的没加载出来。两者在 `did-fail-load`
> 那一刻**长得一模一样**。所以判定要**等 1.2 秒**（`FAIL_GRACE_MS`）：期间只要主框架
> 提交成功，就把这次失败丢掉。不这么做，站点的正常跳转会在屏幕上闪出一张**假的**错误卡片。

### 4. 面板那一行小字会说真话

注入的 ⇄ 面板每个页面条目多了一行 `note`（告警时是琥珀色 + `⚠`）：
没加载成功的原因 / 实际停在了哪个域 / 站点返回了什么码。**说不清就写出来，不许让 ✓ 撒谎。**

## 三、★ 顺便说清：站点那边也有它自己的问题

排查时实测（curl 直连）：`https://platform.deepseek.com/` 与 `https://chat.deepseek.com/`
**都返回 `429 Too Many Requests`**，正文是华为云 WAF 的拦截页：

```
HTTP/1.1 429 Too Many Requests
Server: CW
Block-Event-Id: 08-clou-199-20260922024134-252937ba
<title>Error - Request Blocked</title>
```

**这台机器（或这条出口线路）当时被站点的 WAF 挡了** —— 这不是客户端能修的。
所以这一版修完之后，你看到的会是**一张写着 `HTTP 429`/`ERR_ABORTED` 的卡片**，
而不是一个**看起来正常其实是网页版**的页面。想让它真的能打开：
**换一个 Clash 节点**（出口 IP 就变了）再点一次，通常就好了。

## 四、验收（真跑，`node scripts/ui-check.js pages`）

原来那一段只回读主进程的 `active` **id** —— 所以它在 0.2.6 那个 bug 上**全绿通过**，
是标准的假 PASS。现在加的是**落到那一页自己的视图上**的断言：

```
★ 切到开放平台之后，**可见的那一层**就是 platform（不是 chat 还开着）
★★ 开放平台那一页**绝不会**停在网页版的地址上        ← 用户报的那条 bug 的直接判据
★ 没加载成功时，面板那一行**必须**把原因写出来（不许静默）
★ 失败后那一页换成了**本地错误卡片**（而不是别的站点的页面留着）
★ 错误卡片上写着错误码与重试办法
★ 切到网页版时，可见的是 chat 那一层、platform 那一层收起
★★ 两页互不覆盖：在网页版这一页看到的一定是 chat 的域（或它自己的错误卡片）
★★ 强行制造一次加载失败（把那一页的地址改成必然连不上的 127.0.0.1:9）
   ⇒ 失败被判出来、错误码记下、那一页仍然可见、面板那一行变成告警
★ 再点一次这一页会**真的重试**（错误码不再是那次强行制造的 CONNECTION_REFUSED）
★ 重试在日志里留下新一轮「加载站点」记录
```

★ 最后那三条**故意不依赖站点可达性**：站点通不通都要能验，否则这条判据会随网络时好时坏。
★ `views[id]` 只对外发 `host / http / err / visible`，**不发完整 URL** ——
那个 payload 会经 `dsh:page:list` 回到两个网站页面的脚本里（切换把手要用它），
而登录跳转的路径/查询串上可能带参数。要完整地址的是验收脚本：
它直接去那一页自己的 webContents 上读 `location.href`（最硬的证据）。

## 五、这一版**没有**改什么

- **内核一个字节没动**；外壳仍然零运行时依赖。
- **不拦站点的重定向**（拦了会弄坏登录流程）—— 只在面板上说出真相。
- 站点被 WAF 挡住这件事**客户端修不了**，只能显示清楚。
