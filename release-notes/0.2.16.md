# DSH 集成桌面端 0.2.16

**内核 0.1.7 换了一套模块布局之后，「全新机器」这条路断了一根：新用户装不上任何插件。
这一版修的就是它 —— 顺带把一个我一开始判错的结论改正过来。**

> 用户原话：「关于这几个真的 bug，你修一下吧，最好按照适配官方的样子来修，
> 不然的话新用户还得用老版本的内核。」

## 一、★★ 新用户装不上插件（真 bug，已修）

### 现象

外壳自己的日志（**全新家** + 内核 `0.1.7-rc.2`，从首启向导装插件）：

```
安装插件 dsh-int-archive-manager@0.2.0：ok=false changed=[…]
  profile 的 node_modules 不存在：…\dsh-home\profiles\web\node_modules
```

### 根因：官方换了 profile 的模块布局

| 内核 | `<DSH_HOME>\profiles\web\node_modules` | 我们的落位逻辑 |
|---|---|---|
| `0.1.5` 那代 | 内核启动时装 `@deepseek-ai/dsh-base` 那一套 ⇒ **总是存在** | 有地方可写 ⇒ 正常 |
| `0.1.7` 起 | 模块解析改由 `<DSH_HOME>\profiles\node_modules`（**拦截层**）承担 ⇒ **全新 profile 里根本没有它**，要等 pnpm 真跑过一次才出现 | 一看目录不在就报错返回 ⇒ **装不上** |

★ **开发机上永远复现不出来** —— 那里的 `node_modules` 早就存在了。

### 修法：**按官方的样子**把那个目录自己建出来

新增 `src/plugins.js` 的 `ensureProfileModules(nmDir)`：不存在就建一个**空的**；
位置上若是文件则**拒绝覆盖**。三个入口共用它：

* `src/plugin-install.js` 的 `connectIntoProfile`（首启向导 / 设置页走这条）
* `src/plugins.js` 的 `provision`（随包分发走这条）
* `scripts/install-plugin.js`（开发机用）

**为什么"建一个空目录"是对的，不是绕过**：我们走的本来就是 pnpm 的等价物
（内核的 `dsh-plugin-manager` 装插件时就是 `pnpm add`，pnpm 建的就是这个目录；
profile 的 `pnpm-workspace.yaml` 里 `nodeLinker: hoisted`）。Node 的解析顺序是
`<profile>\node_modules` → `<DSH_HOME>\profiles\node_modules` —— 空目录不影响第二层。
实测真家里那个目录本来就是**实体目录**，pnpm 装的包与我们的联接一直共存。

⚠️ 只建**这一层**。绝不碰 `<DSH_HOME>\profiles\node_modules`（内核的世代拦截层，
内核启动时自己 heal；碰它会重演 2026-09-19 那次跨世代改写事故）。

### 验收：`npm run fresh:check`（新脚本，15 条断言，**真跑两次内核**）

`scripts/fresh-install-check.js` —— 全程临时 `userData` + 临时 `DSH_HOME`，不碰你的环境：

```
实测：全新 profile 的 node_modules 存在=false
PASS  ★ installFromDir 在**全新家**上成功了（修之前这里必失败）
PASS  ★ node_modules 被**自己建出来**了（不是等内核）
PASS  ★ 穿过联接**真读得到** lib/client.js（目录在 ≠ 读得到）  — 63772 字节
PASS  内核的客户端插件清单（__DSH_BOOT__.entries）里真的有 dsh-int-multi-session
PASS  （正对照）entries 不是空的  — entries(65)
[fresh-install] 全部通过（15 条）
```

最后两条最要紧：它**再起一次真内核**，读 `__DSH_BOOT__.entries` 问**内核自己**
「你加载的客户端插件清单里有它吗」—— 不是"文件在那儿"，是内核真的会加载它。

另在 `scripts/plugin-install-check.js` 加了第 ⑪ 段（9 条，两个入口都查，
含一条**回归护栏**：旧那句「profile 的 node_modules 不存在」不许再出现）。
该脚本现在 **114 OK / 0 FAIL**，`provision:check` 仍 **90 OK / 0 FAIL**。

## 二、改正一个我判错的结论：侧栏文件树**不是**冲突

上一轮我报告说「0.1.7 的右侧栏改成了面板列表，我们的侧栏文件注入失效了」。
**实测下来这句话是错的**，我把量具量错了对象：

* 0.1.7 的右侧栏变成了**可停靠的标签坞**。它的默认页规则是
  「注册的标签类型**只有一个**时才默认打开它，**否则落在「指南」页**」——
  一个罗盘 ＋ 每个类型一个入口胶囊。文件树只是其中一个类型
  ⇒ 展开右侧栏**默认看到的是指南**，要点一下「工作区文件」才见文件树。
* **官方那两行 DOM 一个字都没变**：`data-files-entry` / `data-files-path` /
  `data-files-state="tree"` / `data-files-root` 全都在。
* **我们的注入脚本一行都不用改** —— 它监听整个 `document` 的 `mouseover`，
  行一出现就生效。

⇒ 真正要改的是**验收脚本**：`node scripts/ui-check.js files` 从"睡 1.5 秒读一次"
改成「轮询等待 ＋ 若停在指南页就点开 `files` 那个入口 ＋ 失败时打印右侧栏结构快照」。
修完 **「files 模式全部通过」**（含"真鼠标悬停 ⇒ 行尾浮出图标"、
"真点 ⇒ 主进程 `shell.log` 留下独立一行"、以及工作区外 / `..` 穿越被拒的边界）。

★ 顺带踩到并记下的坑：指南入口要点**真的在指针下**的那一个 ——
实测页面里存在**两份**标签坞（`role="tab"` 里「开始」出现两次），
先命中的那份是**隐藏的**，按它的坐标真点等于点空气（第一版就是这么假 FAIL 的）。

**升级到 0.1.7 之后你会看到**：展开右侧栏默认是「指南」页（两个入口：工作区文件 / 新建终端），
点一下「工作区文件」才看到文件树 —— 这是**内核自己的交互改动**，不是我们丢了功能。
文件树一出来，悬停图标与右键菜单照旧。

## 三、顺手回答的那件事：卸载失败**不是冲突**

你在官方界面卸 `dsh-plugin-install` 连试三次都失败。内核把每次插件操作的 pnpm 输出
写在 `<profile>\.plugin-manager\logs\operation-*\pnpm.log`，三份内容完全一样：

```
Error: ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION
  ╰─▶ 2 lockfile entries failed verification:
        dsh-connect-workbuddy@2.1.0 was published at 2026-09-25T03:31:32.687Z
        dsh-qoder-connect@0.1.9     was published at 2026-09-25T07:25:51.742Z
      within the minimumReleaseAge cutoff (2026-09-24T16:50:15.129Z)
```

* **拦住它的是两个毫不相干的插件**；pnpm 校验的是**整份 lockfile**，
  只要有一条"太新"，**任何**插件操作都会被挡。
* `pnpm config get minimum-release-age` → `undefined` ⇒ 这是 **pnpm 12.3.4 自己的默认值
  （24 小时）**，不是谁配的。最早重试时刻：**2026-09-26 15:25:51（本地）**。
* 那次卸载其实**做了一半**：`dsh.profile.bundles` 里已经没有它（**早就不生效了**），
  但 `dependencies` 与 `node_modules` 还在 ⇒ 官方面板照样列着它。

**两条出路**（详见 `docs\内核0.1.7适配-2026-09-26.md`）：
用外壳的「外壳设置 → 集成版插件」卸（那条路**一次 pnpm 都不跑**，改前先备份），
或者过 24 小时再点官方的。

## 四、这一版还顺手加固的两处

* `npm run verify:asar` 给 `src/plugins.js` 与 `src/plugin-install.js`
  加了标记（`ensureProfileModules` 等）—— 这个修复要是将来被谁悄悄改回去，
