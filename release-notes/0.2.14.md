# DSH 集成桌面端 0.2.14

**这一版让新用户「下载完就能用」：外壳自己把 dsh 内核装好，用户不必再敲命令行。**

> 用户原话：「我们这个纯粹的外壳下载之后还得麻烦用户自己去跑命令行下载前面这两个东西
> 才能用，这里就不比社区版简便了。……能不能让官方内核也和插件一样在安装界面勾选，
> 如果用户自己有的话就不用勾，或者就算勾了，扫描到电脑里已经有了，也不会下载，
> 如果没有的话就勾上给他加一句说明就可以了。」

---

## 一、先说清那两个"东西"到底是什么

用户以为要装两个：**Node.js** 和 **dsh 内核**。逐条查过之后：

| 那个"东西" | 真实情况 |
|---|---|
| **Node.js** | ❌ **从来就不需要。** 外壳一直是用 **Electron 自己当 Node** 跑内核的（`src/kernel.js`：`spawn(process.execPath, …, ELECTRON_RUN_AS_NODE:"1")`）。用户以为要装，其实没要过。 |
| **dsh 内核** | ✅ **真缺。** `vendor/dsh` 不存在 ⇒ 发现链只能退到"全局 npm"，而新用户的机器上**没有**它。 |

⇒ 真正要解决的只有**一件事**：怎么在没有 Node.js 的机器上，把内核装上。

### 为什么不是"自动跑一条 npm 命令"

用户原本的想法是「一条自动运行的 npm 指令」。**这条路走不通**：
`npm` 命令本身**需要 Node.js**，而对方机器上没有 ⇒ 死循环。

★ 出路是：**npm 本体是纯 JS**（零平台二进制、11.7 MB），可以随外壳一起带走，
再用 **Electron 自带的 Node** 去跑它。2026-09-25 真跑验证：

```
electron.exe <npm>/bin/npm-cli.js --version   → 11.20.0 ✅
真装一次内核 → 518 个包 / 79 秒 / 212.7 MB，装完内核自报 0.1.5-rc.3 ✅
```

⇒ **"用户要装 Node"这件事彻底消失。**

## 二、做了什么

### 1. 内核落在**用户数据目录**，绝不碰别处

```
<userData>\kernel\<版本>\        ← 外壳自己装的内核住这儿
```

发现链新增一级 **②.5「外壳安装（版本）」**，位置在「应用自带」之后、「全局 npm」之前。
（压过全局 npm 是刻意的：否则用户点了"给我装内核"，外壳却仍去用那个更旧的全局版本，
界面上看就是"装了没生效"。）

### 2. ★★ 四条铁律（每条都对着一次真实事故）

| # | 铁律 | 为什么 |
|---|---|---|
| ① | **绝不装进安装目录** | 社区版把内核嵌进安装目录，于是"升级内核 = 拆自己地基" —— 2026-09-19 那次事故（客户端完全起不来、连逃生通道都失效）就是这么来的。装到用户数据目录 ⇒ 与外壳生命周期完全解耦，`kernel.js` 铁律 1「外壳不拥有内核」**不破**。 |
| ② | **绝不碰 `npm i -g` 的全局目录** | 那会冲掉 `dsh` 的守卫 shim，也会污染用户已有环境。用 `npm install --prefix <私有目录>`。 |
| ③ | **已装就不下载** | 判据复用 `discoverKernel()` —— 它已经会找 `DSH_KERNEL_PATH` / `vendor/dsh` / 全局 npm。找到就**一个字节都不下**（用户明确要求的那条）。 |
| ④ | **绝不自动下载** | 下 214 MB 是件大事，**必须用户点了勾、点了开始**。没有任何"启动时偷偷装"的路径。 |

### 3. 新用户**唯一看得见的那条路**

这是本版最要紧的一处设计，也是我第一版**漏掉**的：

全新机器上 `ensureServer()` 会抛「找不到 dsh 内核」⇒ 用户停在**加载页的失败态**。
**那时他还没进过设置页** —— 所以「设置 → 运行环境」那一栏做得再好也救不了他。

⇒ 新增诊断动作 **`install-kernel`「下载并安装内核」**，并且：

* **只在"这台机器上一个内核都没有"时出现**（有内核时它必须消失，否则诱导用户白下 214 MB）；
* 缺内核时，加载页的「诊断与修复」抽屉**自动拉开**，主标题换成人话
  （「这台电脑上还没有 dsh 内核」）；
* 抽屉**只自动拉一次** —— 用户关掉之后，不会被下一次状态推送又弹开。

### 4. 三种结局**分开报**，不许混成一句"失败"

| 结局 | 报告 |
|---|---|
| 装好 + 发现链认到 + 重启成功 | `ok` |
| **装了，但发现链认不到** | **不报成功**（"文件在那儿" ≠ "装了生效"） |
| 安装本身失败 | 如实报 npm 的退出码与原因 |
| **装好了，但重启失败** | 明说「**已装好**」—— 别让用户以为 214 MB 白下了 |

## 三、★★ 这一版最值得记的一件事：**验收脚本量错了地方**

### 开发机全绿，产物是坏的

`kernel-provision-check`（26 条断言，真下 214 MB 装一遍）**在开发机上跑一万遍都是绿的** ——
因为 `bundledNpmDir()` 在开发机上读的是 `<repo>/runtime/npm`，
而**打包版读的是 `process.resourcesPath/npm`**。**两条路是两个不同的目录。**

⇒ 我补了 `scripts/packaged-npm-check.js`（回读**产物**），第一次跑就抓到：

```
resources/npm 存在: true（418 个文件 / 3.2 MB）     ← 应该是 1944 个 / 11.7 MB
resources/npm/bin/npm-cli.js 存在: true
FAIL  ★★ npm-cli.js 在，但 node_modules 不在 —— 那是个跑不起来的 npm 壳子
```

**`node_modules` 被整个丢掉了。** 用户拿到 exe 后点「下载并安装内核」，
只会得到「随包的 npm 不在（打包时漏了 runtime/npm？）」—— 而我们在开发机上什么都看不见。

### 根因（读源码坐实的，不是猜的）

`node_modules/app-builder-lib/out/util/filter.js:43-45`：

```js
// filter the root node_modules, but not a subnode_modules
if (relative === "node_modules") {
    return false;
}
```

electron-builder 对 `from` 目录下**正好叫 `node_modules`** 的那一层**无条件拒绝**，
而且**不报错、不警告**。`filter: ["**/*"]` 也救不了它 —— 这是在 filter 之前就拦掉的。

**修法**：把里层拆成**第二条** `extraResources`
（`from: runtime/npm/node_modules` → `to: npm/node_modules`），
那样它的相对路径不再是 `"node_modules"`，就能过。

```json
"extraResources": [
  { "from": "runtime/npm", "to": "npm",
    "filter": ["**/*", "!node_modules", "!node_modules/**/*"] },
  { "from": "runtime/npm/node_modules", "to": "npm/node_modules", "filter": ["**/*"] }
]
```

修完：产物 **1944 个文件 / 11.7 MB**，与 `runtime/npm` **文件数一致**。

⇒ 教训：**"开发机上验过"和"产物里是对的"是两件事。**
本项目早就为「外壳代码」立过这条规矩（`verify:asar` 回读 asar），
但**没有覆盖 extraResources 这类"非代码资源"** —— 这次补上了。

### 一条配套的机械断言

`kernel-update-check` 新增 **①.2**：那**两条** `extraResources` 必须成对存在，
少一条就直接 FAIL 并说明 electron-builder 会静默丢 `node_modules`。
（判据的"真跑"版本在 `packaged-npm-check` —— 它会回读产物并**真装一次内核**。）

## 四、★ npm 版本钉在 **11.20.0**，不是最新的 12.x

实测 npm 12.1.0 每次调用都会打一行警告：

```
npm warn cli npm v12.1.0 does not support Node.js v22.21.1.
```

因为两者的 `engines.node` 对不上：

| | `engines.node` | Electron 37.10.3 的 Node 22.21.1 |
|---|---|---|
| npm **12.1.0** | `^22.22.2 \|\| ^24.15.0 \|\| >=26.0.0` | ❌ **不满足** |
| npm **11.20.0** | `^20.17.0 \|\| >=22.9.0` | ✅ 满足 |

它**仍然装得成**（12.1.0 那次也真装成功过），但：

* 那行警告会被我们**原样流进用户的安装日志**，看起来像出了故障；
* "不支持"是上游的**明确声明**，不能拿"这次碰巧成了"当保证。

⇒ 钉 11.20.0，并在 `fetch-npm.js` 里加了 **⑦.5**：静态判 `engines.node` 是否满足。

### ★ 这条判据第一版自己也量错了

第一版它报「Electron 带 Node **24.20.0**」—— 而 24.20.0 是**系统 node** 的版本，
不是 Electron 的。因为脚本是 `node scripts/fetch-npm.js` 跑的，`process.execPath` 是系统 node。

⇒ 改成**去问 Electron 本体**（`electron.exe -e "console.log(process.versions.node)"`）。
改完输出变成「Electron 带 Node 22.21.1 ⇒ 满足」——
**同一个结论，但这次是量对了地方**（又一个"尺子撒谎"的活例，本项目第 N 次）。

### `kernel-provision-check` 新增的两段（⑩ / ⑪）

* **⑩** 不重跑 214 MB，用假 ctx 把**四种结局**都走一遍（成功 / 发现链认不到 / 安装失败 / 重启失败），
  外加三条显隐断言（没内核才有、有内核必消失、状态未知也不显示）。
* **⑪** 源码断言 `main.js` 真的把 `provisionKernel` 注进了 `buildDiagCtx`。
  ★ 为什么这条必须机械钉住：动作在 `diagnostics.js` 里写好了、但 ctx 里没注入的话，
  点下去就是 `ctx.provisionKernel is not a function` —— 而**只有在全新机器上才会暴露**
  （开发机永远有内核，那个按钮根本不出现）。**静态可解析 ≠ 动态可用。**

## 六、边界（说清楚，别以为它比实际更强）

* **不校验内核包的签名** —— 只保证"从官方 `registry.npmjs.org`、经 HTTPS 下载"，
  并按官方 `dist.integrity`（sha512）逐字节校验。
* **只认 `registry.npmjs.org`** —— `registry.npmmirror.com`（淘宝镜像）实测更快，
  但那是**第三方镜像**，加进来等于把"装什么代码进用户的家"交给第三方。
  要加应当是一次**显式的信任决定**。
* **`--ignore-scripts`**：刻意不跑依赖的安装脚本。官方内核的依赖里没有必须编译的原生模块
  （实测装完直接能跑），而跑脚本意味着"下载任意代码并执行"。
  ⚠️ 若将来某版内核真需要编译，这一条要重新评估（那时会有明确报错，不会静默坏）。
* **装内核 ≠ 升内核**：这里只做**新装到独立目录**。
  升级全局 npm 里那份仍然只给命令、由用户自己执行（见 0.2.9 那一节的理由）。
* **首启向导里没有"装内核"按钮** —— 结构上做不到：那一屏排在 `ensureServer()` **成功之后**
  （勾选装插件要写 profile，而 profile 是内核第一次跑起来才建的）。
  走到那一屏时内核**必然已经在了**，勾选框永远是"已扫到 ⇒ 不下载"那一个分支。
  所以那一屏只**如实报状态**（「✓ 已经有内核了…不会重复下载」），
  真正需要装内核的人走的是**加载页失败态**与**设置 → 运行环境**两条路。
