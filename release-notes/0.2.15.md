# DSH 集成桌面端 0.2.15

**一趟查下来挖出两件事：①「检查内核更新」只问了 npm 的一个标签，整个 0.1.7 系列看不见；
② 更要紧的是，0.1.7 在外壳上根本起不来 —— 而修好它只需要把外壳的 Electron 换成对的版本。
这一版两件都做了。**

> 用户原话：「话说你这个检查内核更新的功能可靠吗？我现在只检测到了一个 0.1.5 的一个小版本，
> 但是现在不是已经跑到 0.1.7 了吗？」

---

## 一、先回答原问题：**功能没撒谎，是信息来源选窄了**

直连 `registry.npmjs.org` 实测（不经外壳、不经代理工具）：

```
dist-tags = { latest: "0.1.5-rc.3", next: "0.1.7-rc.2", alpha: "0.1.7-alpha.2" }

0.1.7-rc.2   2026-09-24T14:18Z      ← 确实存在，而且更新
0.1.5-rc.3   2026-09-22T05:55Z
```

旧代码（`src/kernel-update.js`）查的是 `…/@deepseek-ai/dsh/latest`，读 `meta.version`。
按 `latest` 标签算，「官方最新 = 0.1.5-rc.3」这句是**真的**——
**没有缓存坏、没有代理坏、没有拿错包。** 错的是它**只问了那一个标签**，
于是把"正式渠道推荐的那版"说成"官方最新"，0.1.7 整个看不见。

⇒ 现在读**整份元数据**（npm 精简格式，实测 ~145 KB，`dist-tags` 与每个版本的 `dist` 一个不少），
把**全部发行渠道都列出来**，各自标「比本机新 / 旧 / 同版本」，并点名比正式渠道更新的那些。

### 三条口径写死在界面上

| | 说明 |
|---|---|
| **默认渠道仍是 `latest`** | 不替用户把预览渠道当默认 |
| **`npm i -g @deepseek-ai/dsh` 只装 `latest`** | 所以命令行**装不到** 0.1.7。要装别的渠道只能用下载下来的那个 `.tgz`（版本钉在文件名上） |
| **全部渠道里最高的那版，官方没提升它** | 界面写明「它不在正式渠道上」—— 这是事实，不是我们的判断 |

## 二、★★ 真正的答案在第二层：0.1.7 起不来 —— 以及为什么

渠道清单做出来之后立刻浮出更要紧的一问：**这些版本真的能跑吗？**
按 `$DSH_HOME/AGENTS.md` 第二条铁律（"必须真让它工作"），没有推断，全部真跑
（新工具 `scripts/kernel-compat-check.js`，每条都是一次真启动）。

### 第一轮：外壳当时带 Electron **37.10.3**

| 内核版本 | 渠道 | 结果 |
|---|---|---|
| `0.1.5-rc.2` | （本机在用） | ✅ 就绪 |
| `0.1.5-rc.3` | `latest` | ✅ 就绪 |
| **`0.1.7-rc.2`** | **`next`** | ❌ **`Unsupported/no-context`** |
| `0.1.7-alpha.2` | `alpha` | ❌ 同上 |
| `0.1.7-rc.2` | 改用**系统 node 24** 跑（对照） | ✅ 就绪 ⇒ **卡的是 Electron，不是内核本身** |

内核自己打出来的原文：

```
dsh: fatal uncaught exception: Error: dsh: host preparation failed:
node-addon-require-builtin unsupported: Unsupported/no-context
(unsupported Electron runtime fingerprint: Node 22.21.1,
 V8 13.8.258.32-electron.0 (supported Electron versions: 43.0.0, 44.0.0, 45.0.0-alpha.6))
```

表现是加载页**永远停在「正在等待内核就绪…」**，日志里只有这一行 fatal。

### 机制（逐文件数出来的，不是猜的）

| 内核 | `dsh-app-boot/lib/index.js` 里 `installRuntimeInterception` |
|---|---|
| `0.1.5-rc.3` | **0 处**（根本没有这个调用） |
| `0.1.7-rc.2` | **3 处**（`requireBuiltin` 相关 5 处） |

⇒ **`0.1.6` 起内核新增了运行时拦截**：要 hook V8 内部去 `require` 内置模块，
而它依赖的 `node-addon-native-custom-loader@0.1.6` 只认
`43.0.0 / 44.0.0 / 45.0.0-alpha.6` 的**精确**运行时指纹。
两个内核带的是**同一个** 0.1.6 版加载器 ⇒ **差别在调用方**。

### 第二轮：把外壳升到 Electron **44.0.0** ⇒ 四个版本**全部 ✅ 就绪**

**0.1.6+ 内核因此可用。** 这一版外壳顺带解开了它。

## 三、★★ 最容易踩错的一步：**「升到最新」在这里是错的**

第一次尝试升 Electron 时，很自然地装了当时的最新 **44.4.5** —— **照样起不来**：

```
unsupported Electron runtime fingerprint: Node 24.21.0, V8 15.2.124.28-electron.0
(supported Electron versions: 43.0.0, 44.0.0, 45.0.0-alpha.6)
```

那个校验比的是 **V8 运行时的精确指纹**，**不是版本区间**。
`44.4.5` 与 `44.0.0` 的大版本一样、补丁号不同 —— 但在它眼里是两种运行时。

⇒ 两条硬结论，都写进了代码与断言：

1. **`package.json` 里 `electron` 是精确钉死的（`"44.0.0"`，不带 `^`）**，
   旁边加了 `//electron` 说明"为什么不能加 `^`、也不能顺手升到最新"。
2. `scripts/kernel-update-check.js` 的 **②.6** 有一条断言盯着
   「外壳的 Electron 在加载器的支持列表里」—— 漂到 44.4.5 会直接 FAIL 并说明原因。

★ 另外查过一条出路是**没有**的：那个加载器在 npm 上的**最新版就是 0.1.6**（2026-09-14 发布）
⇒ 不存在"换个新加载器就能支持更多 Electron"这条路。

## 四、界面多了「能不能跑」这一栏，而且**证据等级写在脸上**

`channelsFromMeta()` 是**纯函数**，`compatOf(version, electron)` 判**五档**：

| 等级 | 含义 |
|---|---|
| `verified-ok` / `verified-bad` | 这一版在**当前 Electron**上**真跑过** |
| `known-bad-electron` | 这一版没跑过，但外壳这个 Electron **真跑过跑不了**（如 44.4.5） |
| `gen-ok` | Electron 在加载器支持列表里 ⇒ 这一代内核**预计**能跑 |
| `unknown` | 都不沾边，`usable: null` —— **说不出能不能跑**，界面不许猜 |

★ 绝不把"预计"或"同世代"写成"实测"——那正是本项目记过两次的
「拿代理证据当通过凭据」。

界面上：

* 「起不来」的渠道那一行**变红**，写明要哪几个 Electron；
* 说明区点破「装了会让客户端起不来 —— 想拿文件可以下，**别装**」；
* 下载区顶一条红字说明那条命令只用来把文件拿到手；
* 非默认渠道的下载确认框里也带这句警告。

## 五、★ 为什么把渠道解析做成纯函数

用户报的那个 bug **不该靠"此刻 registry 上恰好有什么"去验** ——
上游哪天把 `latest` 提升到 0.1.7，真跑断言就自动变成"验不到"，护栏失效。

⇒ `channelsFromMeta(meta, cur, opts)` 不联网、不读盘、不看时钟。
验收脚本喂一份**与 2026-09-25 那天完全相同**的元数据，离线且**永远可复现**地断言：

* 三个标签一个都没漏；
* `0.1.7-rc.2` 出现在结果里、被标成「比默认渠道新」**并且**「实测能跑」；
* 默认渠道仍然是 `latest=0.1.5-rc.3`。

### 配套的「护栏的护栏」

`COMPAT_EVIDENCE` 每条都钉着**验它时的 Electron 版本**，`kernel-update-check`
断言「记录与本机 Electron 不符就 FAIL」，逼你重新真跑 —— 这次升 Electron 时它**当场就 FAIL 了**，
正是设计意图。另外 `COMPAT_KNOWN_BAD_ELECTRON` 记着 37.10.3 与 44.4.5 两个"实测跑不了"的版本，
免得将来有人再试一次。

## 六、新增两个可复用的工具

```powershell
# ① 某一版官方内核能不能跟外壳一起跑？（真装 + 真启动，判据是"拿到本机地址"）
node scripts/kernel-compat-check.js --version=0.1.7-rc.2
node scripts/kernel-compat-check.js --version=0.1.5-rc.3 --version=0.1.7-rc.2
node scripts/kernel-compat-check.js --version=0.1.7-rc.2 --runtime=node      # 对照组：换系统 node
node scripts/kernel-compat-check.js --version=0.1.7-rc.2 --electron=<目录>    # 换一版 Electron 试
#   退出码 0=能跑 2=起不来 3=装不上 4=用法错

# ② 让**既有的界面验收**在指定版本内核 / 指定 Electron 上原地跑一遍
node scripts/ui-check.js loading --kernel=0.1.5-rc.3
node scripts/ui-check.js pages   --kernel=0.1.7-rc.2
node scripts/ui-check.js pages   --electron="C:\path\to\electron44"
```

`--kernel=<版本>` 用的是**外壳自己那条装内核的路**（`kernel-provision.js`），
装进 `<临时 userData>\kernel\<版本>\` ⇒ 发现链 **②.5 级「外壳安装」**（排在全局 npm 之前）
会优先选中它。判据落在 `shell.log` 的 `使用内核:` 与 `内核就绪:` 两行 ——
**不是"我们把它装上了"**。

★ 两个工具全程只写 `%TEMP%`：不碰用户正在用的内核、不碰全局 npm、不碰 B / A 两个 DSH 家。
★ 这次升 Electron 就是靠它们先验的：**先用临时装的 Electron 44.0.0 跑遍四个界面模式
（loading / plugins / pages / files 全过），才去动 `package.json`。**

## 七、顺手修一个**被自己踩出来的**坑：磁盘满了只会报「npm 退出码 1」

验收跑到一半，`kernel:provision:check` 突然 `8 OK / 1 FAIL`，失败原因就一句
**「npm 退出码 1」**。我刚换完 Electron，第一反应是"升级把安装弄坏了"。

**真因是 C 盘被我自己的临时内核安装塞满了**（只剩 0.2 GB），npm 日志里全是
`ENOSPC: no space left on device`，而 `EBADF: bad file descriptor` 只是它的连带反应。
清理掉 3.7 GB 临时目录之后，同一条命令 **43 OK / 0 FAIL** —— **不是 Electron 的问题**。

⇒ 但**用户遇到这个场景时看到的和当时的我一模一样**：一句「npm 退出码 1」，
原因埋在 npm 自己的日志里。所以补了三件事：

| 补的 | 作用 |
|---|---|
| **动手前先量磁盘**（`fs.statfsSync`，零依赖） | 不够就**当场**说：「装内核需要约 300 MB 空闲，而目标盘只剩 X MB」 |
| **量不到就 `null`** | 不知道就不说话，也**不因此阻断**安装（不编） |
| **认 npm 输出里的 `ENOSPC`** | 万一还是撞上，把「退出码 1」翻译成「磁盘空间不够」 |

`kernel-provision-check` 为此加了 **⑫ 段 7 条断言**（含"空间够就不许弹废话"、
"量不到返回 null"、"认得出 ENOSPC 但不误判 EACCES"）。

★ 记这一段的理由和记别的坑一样：**「我的量具/环境撒谎」比 bug 本身更值得写下来。**
我差一点就把"Electron 升级导致安装失败"写进这份发布说明。

## 九、边界（说清楚，别以为它比实际更强）

* **没有"自动帮用户升级内核"** —— 与 0.2.9 起的边界一致：只**下载 + 按官方 sha512 校验 + 给命令**，
  命令由用户在自己的终端里执行。理由见 `release-notes/0.2.9.md`（2026-09-19 的事故）。
* **「能不能跑」不是通用检测器** —— 唯一可靠的办法是 `kernel-compat-check.js` 真跑一次。
  界面上的判定只覆盖**验过的版本 + 支持列表 + 已知跑不了的 Electron**，
  并且每一档都会说清是"实测"还是"预计"还是"未验"。
* **升 Electron 的代价要记住**：精确钉版意味着**拿不到 44.x 后续补丁**。
  这是"能跑 0.1.6+ 内核"换来的 —— 上游哪天放宽指纹校验，就可以回到 `^`。
  （相对之前那版 Electron 37.10.3，44.0.0 本身仍是一次大幅前进。）
* **`kernel-provision.js` 装内核时仍然只查 `latest`** —— 那是刻意的：
  那一段的语义是"新装一个能用的内核"，装正式渠道那一版是对的；
  "看得见有哪些版本"是 `kernel-update.js` 渠道清单的事。两处都留了注释说明。
